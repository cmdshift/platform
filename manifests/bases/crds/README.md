# crds

Upstream CRD kustomizations (cloudnative-pg, gateway-api) installed ahead of the operators that use them.

## Rules

- **Never prune**: deleting a CRD destroys every CR of that kind cluster-wide — CRD removal must be deliberate and coordinated, never git-driven. Each child kustomization carries the same `prune: false`-class posture; upstream CRD churn between releases would otherwise delete every CR of the kind (Gateway/HTTPRoute, Cluster/Backup).
- The GitRepository tags for `cloudnative-pg-crds` must move **in lockstep with the matching chart version** — the CRDs must match the operator's API surface.
- Operators whose charts ship CRDs in the chart's `crds/` directory (valkey, strimzi) need **no entry here**: helm-controller installs `crds/` content with the release (and it never enters the release secret, so the 1MB cap doesn't apply); chart CRD **upgrades** require the HelmRelease's `install.crds: Create` + `upgrade.crds: CreateReplace` policy (flux defaults to create-only). Only charts that render CRDs from `templates/` (cloudnative-pg) need the child-kustomization + lockstep-tag pattern.
- **Deleting a child Kustomization object cascades its CRDs** — the finalizer GCs all managed inventory on object deletion even when the child carries `prune: false` (`prune: false` governs drift removal during reconcile, not deletion). Verified live: removing the emqx child in cmdshift/platform#166 took the `emqx.io` CRDs down with it, no hand sweep. So the "never prune" rule above is stronger than the `prune: false` posture: **CRD removal CAN be git-driven — any change that removes the child object (deleting its file, or dropping it from this group's list; the root's `prune: true` then prunes the object) destroys every CR of that kind cluster-wide. Never let that happen accidentally.** The only non-destructive way to orphan a child's CRDs is removing the CRD files from the child's own `resources:` list (object survives, `prune: false` doesn't drift-prune) — that's the pattern if CRDs must be unmanaged but kept. Any change to the crds group's children is a coordinated CRD-lifecycle event, never incidental cleanup.
