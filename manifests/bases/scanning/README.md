# scanning

trivy-operator (static posture scanning) + `scanning-config/` (vendored ClusterComplianceReport specs). Split out of `security/` (cmdshift/platform#60) so tetragon's dependency set stays minimal and `security` can bootstrap early — the rebuild-ordering landmine in [security/README.md](../security/README.md) is the reason this group exists.

## Contents

- `trivy-operator.helm-release.yaml` — chart 0.38.1, `aqua` HelmRepository. Includes the built-in trivy-server (StatefulSet, 5Gi local-path PVC for the trivy-db cache — the `security` group's old storage-config dependency was entirely this; local-path cannot expand in place, keep headroom for the ~3GB DB-update double-buffer).
- `scanning-config/` — the vendored compliance specs (NSA, PSS baseline/restricted), moved verbatim from `security-config/`. Re-vendor deliberately on chart bumps.

## Group mechanics

- The scan Jobs exec `/bin/sh -c` wrappers by design (operator-generated; no values knob) — `allow-trivy-scan-jobs` in `policies-config/` excepts them from `deny-shell-entrypoint`, namespace-scoped to `scanning`. They also escape pod-scoped tetragon enforcement (container-init gap), so `exec-deny-list-scanning` covers only the operator + server pods.
- Scan jobs are spawned on the operator's re-scan cycle (periodic + report-refresh); `scanJobTTL: 10m` GCs them. A `policy_report` failure spike on just-finished scan pods is usually the TTL window racing the background scan — re-check after the TTL expires before diagnosing. Migration trap (live): Jobs stranded in the operator's OLD namespace when it moved here were never TTL-reaped (the reaper died in the prune-uninstall) and the `allow-trivy-scan-jobs` exception (namespace=='scanning') can't skip them — completed operator-orphan Jobs in old namespaces flag forever until deleted.
- **The wholesale re-scan flood after any bump is the 24h report TTL purge, not the scanner bump** (cmdshift/platform#262): `OPERATOR_SCANNER_REPORT_TTL=24h` GCs reports older than 24h and re-queues their workloads — a batch expiring at once re-queues ~90 workloads at `scanJobsConcurrentLimit` 3 / ~10-min-per-scan ≈ 5-6h drain. That's the expected shape, not a wedge. The scan-slot race is unfair (single channel goroutine): under a big queue a workload can starve for hours (observed 4.5h) — waiting is the sanctioned fix, no intervention.
- **A workload can reconcile "green" while its scan silently never requeues** (cmdshift/platform#262): scan-job names are deterministic (`scan-vulnerabilityreport-<hash(owner)>`) — a stale COMPLETED job makes the re-submit Create hit `AlreadyExists`, which is silently swallowed, so the workload reconciles without a scan until the stale job TTL-GCs or the operator restarts. Same silent skip when a template change lands while pods are still creating (`ErrNoRunningPods` → skip, no requeue). The operator's startup sync re-enqueues everything missing current-revision reports — `kubectl rollout restart deploy/trivy-operator -n scanning` is the sanctioned recovery (same pattern as the config-cache trap below).
- **Report creationTimestamp is NOT scan freshness** (cmdshift/platform#262): report objects persist across template revisions via in-place updates, which preserve creationTimestamp — judge freshness by the report's artifact tag/digest and its `resource-spec-hash` label instead.
- `Unable to parse container` WARNs in the operator log are the compliance/SBOM flow tripping on pods mid-creation (empty imageID digest) — harmless for vulnerability reports (cmdshift/platform#262).
- **Vulnerability-alert surface restored** (cmdshift/platform#242): `trivy_critical_image_vulnerabilities` is back in the openobserve-sync alert set (starting shape from the removed o2-sync era's JSON at git `5bb7c5a^`, namespace regex now includes `datastores|scanning`); CRITICAL-only by design with `max_over_time(30m)` so the alert holds through rescan-gap flaps (cmdshift/platform#36). Two landmines found restoring it: **(a) the security→scanning split broke the observability gateway's trivy-operator scrape relabel — the namespace keep-filter stayed pinned to `security`, so the `trivy_image_vulnerabilities` stream never materialized and the alert was unparkable; group splits must sweep the observability gateway's scrape relabels too (cmdshift/platform#171); (b) the metrics Service is headless (chart default) so the gateway's scrape job needs `role: endpoints` — `role: service` resolves headless DNS to the pod IP and dials the declared service port 80, while the operator serves metrics on 8080 behind a named targetPort that never resolves — silent `connection refused` / `up=0` forever.**
- **CNP trap: the security→scanning split dropped the intra-ns `:4954` rule** (cmdshift/platform#171, live finding): the pre-split security CNP allowed pod→trivy-server (`:4954`, operator health check + scan-job DB pulls); the first-cut scanning CNP carried only kube-apiserver/registry/world — the operator's `TrivyServerAvaliable()` probe was Cilium-dropped, the negative result cached (`TRIVY_SERVER_HEALTH_CHECK_CACHE_EXPIRATION`, 10h), and vuln submission silently requeued at V(1) — **zero scan jobs, zero reports, no loud errors**. Restored the intra-ns rule. Debug ritual: `logDevMode: true` exposes the V(1) decision points; probe the server port from a pod in the namespace before assuming an operator bug.
- **Scan jobs run in the operator's namespace (chart default)** (cmdshift/platform#181): `scanJobsInSameNamespace` is left at its default (`false`) so scan jobs spawn in `scanning` — under the scanning CNP's egress, the `allow-trivy-scan-jobs` PolicyException, and the resource quota — instead of in each scanned workload's namespace, where they had **no CNP egress coverage** and were denied by `deny-shell-entrypoint` (kube-system/flux-system/policies were live findings). Watch the reload trap: a values-only edit + reconcile updates the release, but the operator **caches the trivy config at startup** — if new scan jobs still land in target namespaces after a green reconcile, `kubectl rollout restart deploy/trivy-operator -n scanning`.
- Namespace PSS is `privileged` to match the old security-ns posture the scan jobs were deployed under; revisit for `restricted` once the chart's job template is audited end-to-end (see the namespace comment).
- The chart hardcodes the built-in server URL to the operator's own namespace (`trivy.serverURL` is only honored in non-builtin mode) — server and operator must stay co-located unless a postRenderers patch is added.
- Namespace PSS posture rationale (migrated from the namespace manifest): privileged matches the old security-ns posture the scan jobs were deployed under — scan pods run non-root 65534 via `scanJobPodTemplate*`, but the chart also renders admission-controller-mutating scaffolding that predates the hardening pass; kyverno deviations scoped by `allow-trivy-scan-jobs`. Also in [namespaces/README.md](../namespaces/README.md).
- `scanning.resource-quota.yaml`: trivy-operator + trivy-server + up to 3 concurrent scan jobs (`scanJobsConcurrentLimit`) — scan bursts peak ~768Mi each; headroom for one rollout overlap (cmdshift/platform#93).
- **`trivy.image.tag: "0.76.2"` is a deliberate override on top of chart 0.38.1** (cmdshift/platform#263): chart 0.38.1 defaults trivy 0.76.1, whose image was built before the Alpine 3.24.3 security rebuild (commit `ae26b88`) and still carries vulnerable `brotli-libs 1.2.0-r0` (CVE-2026-111497) — same build-date trap as kustomize-controller v1.9.6. The fix is trivy 0.76.2 (live-verified: `apk info brotli-libs` → 1.2.1-r0, alpine 3.24.3). Supported combo: the operator (0.34.0) invokes trivy with `--format json` so the only 0.74→0.76 break (sprig `getHostByName` removal from report templates, aquasecurity/trivy#11206) doesn't apply; server and scan jobs share the tag (no version skew); the 5Gi cache PVC stays valid. **Removal condition: drop the tag when the next chart defaults trivy ≥ 0.76.2** (tracked in cmdshift/platform#263). 0.76.2 is a fresh tag → no pull-through-cache staleness concern (unlike the strimzi re-pushed tag).
- trivy-values evidence (`clusters/local/scanning/trivy-values.yaml`): `dbRepositoryInsecure: "true"` (the cache is plain HTTP via haproxy); the `trivy.registry.mirror` map lists both `docker.io` and `index.docker.io` (the normalized form of docker.io refs — both needed); the 5Gi PVC has no expansion headroom to spare (local-path cannot expand in place — peak ~3GB during DB update double-buffering); `scanJobsInSameNamespace` stays at chart default `false` so scan jobs spawn in `scanning` under the scanning CNP (cmdshift/platform#181); operator sizing re-audited on the O2 RSS store — 7d P99 283Mi / max 333Mi, VPA target 454Mi → request 448Mi (max(P99×1.2, VPA)), limit 672Mi = 1.5×; the old 496Mi hourly-burst figure is not in the current 7d window (cmdshift/platform#219).
