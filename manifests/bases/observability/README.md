# observability

OpenObserve is the observability stack (cmdshift/platform#171 — replaces the LGTM stack: mimir/loki/tempo/grafana + seaweedfs, which existed only to serve them; the `objects/` group went with it). The group keeps: **openobserve** (`openobserve-standalone` chart 1.0.1 — single node, SQLite metadata on local-path PVC, parquet data in rustfs S3), **two collector HelmReleases** from the plain `otel/opentelemetry-collector` chart 0.175.0 (agent DaemonSet + gateway Deployment — see below why two), and the sizing stack (metrics-server, vpa — both install into kube-system but their HelmReleases/values live here by domain). kube-state-metrics remains a standalone release (the agent collector's `clusterMetrics` preset bundles its own ksm; the gateway scrapes the standalone one). Alertmanager was removed (cmdshift/platform#182) — O2 native alerts deliver via O2's built-in SMTP directly to the mailpit companion.

Grafana is dropped — O2's built-in UI serves dashboards, gated by the `openobserve-auth-proxy` cookie-gate ([access/README.md](../access/README.md)). Dashboards, alert destinations, stream manifests, and alerts are GitOps-synced again by the **`openobserve-sync` Job** (`observability-config/openobserve-sync/`, restored 2026-11-12 — [openobserve-sync](#openobserve-sync-restored-2026-11-12-cmdshiftplatform206)).

**Store decision (cmdshift/platform#186, resolving #171's store gap)**: O2 is the queryable metrics AND log store — its Prometheus-compat API (`/api/default/prometheus/api/v1/...`, Basic auth, org hardcoded `default`, no `X-Scope-OrgID`) backs `prometheus_query` and `cpu_audit`'s throttle check, and its `_search` SQL API (same auth/org) backs `log_query` (cmdshift/platform#203 — replaced the retired `loki_query`). Tooling caveats: the OTel receiver translates standard target labels (`job` → `service_name`, `instance` → `service_instance_id`) while metric-defined labels survive; range-query gap clusters are environment outages, not query bugs (host sleep / store-companion death — cmdshift/platform#202); all container logs land in the single `k8s_logs` stream (event fields INSIDE `body`, k8s identity as flat columns). Auth is the `O2_AUTH_BASIC` key of `secret/openobserve-credentials` — derived in the secrets-server payload from the root credential (no inlined tokens anywhere; [credentials](#credentials-secret-driven)).

Namespace layout rationale (cmdshift/platform#120): the former metrics/monitoring/logging groups merged into `observability` + `observability-config`.

## Architecture

```
workload logs/filelogs + host/kubelet/node metrics ─ agent DaemonSet ─┐
OTLP (traces, app metrics) ─────────────────────────── gateway Dep ───┤
prometheus scrape families (hand-expressed) ────────── gateway Dep ───┼→ openobserve :5080
                                                                        │   (SQLite meta on local-path,
thin detectors (stream+threshold) ──────────────────────────────────────┘    parquet in rustfs)
     │ O2 native alerts → O2 built-in SMTP (ZO_SMTP_* env) → :25 passthrough
   mailpit
```

- **`openobserve`** — `openobserve-standalone` 1.0.1, `fullnameOverride: openobserve`, PVC 5Gi local-path holds SQLite + WAL + query cache only (`ZO_LOCAL_MODE_STORAGE: s3` → rustfs `http://s3.cloud.test`, bucket `openobserve`, region `local`, path-style). Credentials via ExternalSecrets (`openobserve-credentials` root user + derived `O2_AUTH_BASIC` header, `openobserve-s3-credentials` S3 quartet) feeding `extraEnv` — the chart renders `auth.existingRootUserSecret` and empty `ZO_S3_*` placeholders; explicit env beats envFrom. An `emptyDir` at `/tmp` rides `extraVolumes` — O2 writes temp files there and the pod ships `readOnlyRootFilesystem: true` (cmdshift/platform#209: restart/recreate crashed without it).
- **`openobserve-collector` (agent, daemonset)** — filelog (pod logs) + a second `filelog/audit` tailing the apiserver's audit files (ctrl only, cmdshift/platform#208), hostmetrics, kubeletstats, kubernetesAttributes, clusterMetrics presets; pushes to `http://openobserve.observability.svc:5080/api/default/` via `otlphttp` (logs → `k8s_logs`, audit → `k8s_audit`); all ingest ports closed (it receives nothing).
- **`openobserve-collector-gateway` (deployment)** — OTLP ingest 4317/4318 (traces + app metrics; the old tempo intake shape) + hand-expressed `prometheus` scrape_configs ported 1:1 from the deleted `alloy-telemetry.config.alloy` (job names are load-bearing — the o2 community dashboards/alerts select on them).
- **NOT the o2 `openobserve-collector` chart 0.5.0** — it requires the opentelemetry-operator, and there was no CRD-free path through it; the human rejected an operator for this. The plain `otel/opentelemetry-collector` chart has `mode` + `config` **release-global**, so one HelmRelease per mode: agent (daemonset) + gateway (deployment) are two releases in one file (`openobserve-collector.helm-release.yaml`).

## O2 chart landmines

- **The standalone chart's config CM is a HARDCODED KEY ALLOWLIST** — unknown `config.*` values are silently dropped (no error anywhere). Env-only flags must ride `extraEnv` (cmdshift/platform#171). The allowlist contains **ZERO SMTP keys** — all five `ZO_SMTP_*` settings (ENABLED/HOST/PORT/FROM_EMAIL/ENCRYPTION) ride `extraEnv` (cmdshift/platform#182); a `config:` attempt is silently dropped.
- **Alert delivery is O2 built-in SMTP, no alertmanager** (cmdshift/platform#182): the alertmanager HelmRelease/values were deleted; O2 emails destinations directly through the `ZO_SMTP_*` env to the mailpit companion (`ZO_SMTP_ENCRYPTION: ""` is the documented plain-SMTP mode — port 25, local relay). `ZO_SKIP_SSRF_CHECKS` was removed with it — no in-cluster webhook destinations remain; re-add it only if a destination ever points in-cluster again.
- **O2 email destination schema (chart 1.0.1)**: `{"name", "type": "email", "emails": [recipients], "template" (optional)}` — there are **NO per-destination SMTP fields**; transport is the global `ZO_SMTP_*` env. Recipients must be org members; the root user is implicitly a member, and the O2 root user is `admin@cloud.test` (one admin identity across rauthy + O2 — set in `cluster/local/secrets/locals.tf`).
- **The `POST /api/{org}/<stream>/_json` endpoint is LOGS-ONLY** (cmdshift/platform#182, cost multiple debugging rounds): seeding a *metrics* stream name through it materializes a phantom LOGS stream under the same name, which the v2 alerts API (binding on the alert's `stream_type`) still reports as `Stream not found` (404). Metrics streams must be seeded via `POST /api/{org}/ingest/metrics/_json` with body `[{"__name__":"<stream_name>","__type__":"gauge","value":0,"_timestamp":...}]` — `__name__` carries the stream name, `__type__` locks on the first record. Streams auto-create on first ingest of the correct type; the openobserve-sync Job seeds before alert creation, existence-gated via `GET streams?type=<type>` (metrics seed value 0 so no alert condition can fire on the seed). The mechanics are preserved here and encoded in the Job's script (`observability-config/openobserve-sync/scripts/sync.sh`, cmdshift/platform#206).
- **`ZO_COMPACT_DATA_RETENTION_DAYS` defaults to 3650** — a silent disk-full waiting to happen. Set `"10"` (cmdshift/platform#186, bumped from 3d: the vpa_recs/resource-sizing calibration wants ≥10d of trend history; disk gate checked first — the rustfs docker volume's host disk had 168GB free of 230GB). **Retention lives inside the compactor module** (`src/service/compact/retention.rs`) — compaction OFF silently disables data retention entirely (cmdshift/platform#182: `ZO_COMPACT_ENABLED` must stay true or retention is dead).
- **Compaction merges failed every cycle with `Invalid cross-device link (os error 18)` — FIXED** (found live 2026-11-19 while root-causing cmdshift/platform#202): the compactor's cache-set path renames a download temp file from `ZO_DATA_TMP_DIR` (default `<data_dir>/tmp/` → `/data/tmp` on the data PVC) to `ZO_DATA_CACHE_DIR` (`/var/lib/openobserve-cache` on the cache volume) — different mounts, so every merge logged `[COMPACT] download file to cache err … skip file` and skipped its source files. Fix: `extraEnv` `ZO_DATA_TMP_DIR: "/var/lib/openobserve-cache/tmp/"` — same volume as the cache (it can't ride `config:` — not in the chart's key allowlist). Shape verified against O2 v1.1.2 source (`compaction/src/merge/file.rs` write_tmp_file→set rename; the eviction trash already lives inside the cache root; the startup scan skips `.tmp` extensions; the tmp dir is wiped at every start). Not the cause of cmdshift/platform#202's sparsity — those holes are environment-outage windows (see the `prometheus_query` caveats in tools/bin/README.md).
- **Image registry: point at the real home, never a façade** — `o2cr.ai` is a 302 redirect façade to `public.ecr.aws/zinclabs/openobserve`; docker CLI follows cross-registry redirects but **angos does not** (cache-miss returns `not found`; no redirect-following/host-override knob exists in angos v1.12.2 — checked docs+source). Values use `public.ecr.aws/zinclabs/openobserve` (the already-mapped `ecr` upstream); there is deliberately **no o2cr.ai stanza in `registry_map`** (`cluster/local/registry/locals.tf`). Applies to any future image whose host is a redirect façade.
- Chart pin: `openobserve-standalone` 1.0.1 — SQLite metadata migration chains break across minor bumps; test on a fork of the PVC before bumping (cmdshift/platform#171).
- **FSTree sizing** (cmdshift/platform#182): `ZO_MEMORY_CACHE_MAX_SIZE`/`ZO_MEMORY_CACHE_DATAFUSION_MAX_SIZE` are 1536/1536 and the disk cache (`ZO_DISK_CACHE_*`) is the relief valve — 1Gi of the 5Gi PVC, leaving the rest for SQLite + WAL. Memory caches compete with ingest for the same limit.
- **Pod annotations**: `backup.velero.io/backup-volumes-excludes: data` — the data PVC holds disposable SQLite metadata + WAL/parquet staging (data lives in rustfs; dashboards/alerts re-sync via the openobserve-sync Job — see [openobserve-sync](#openobserve-sync-restored-2026-11-12-cmdshiftplatform206)); backing it up live fails ~90% through with an empty data-path error and burns ~7GB of kopia churn per backup (cmdshift/platform#171).
- **Resources**: request 500m CPU / 2Gi mem, limit 4 CPU / 7Gi mem. CPU lean because the quota charges requests (the old 2-core request ate 2/3 of the 3-cpu budget) and O2 reads host cores anyway; the 4-core limit is the burst cap (cmdshift/platform#182). Memory realigned to evidence in cmdshift/platform#219: 7d P99 1562Mi x 1.2 = 1875Mi, VPA target 1850Mi -> 2Gi request (the old 5Gi was ~3x the working set). The 7Gi limit is NOT re-derived at 1.5x — the internal cache budgets (`ZO_MEMORY_CACHE_MAX_SIZE`/`ZO_MEMORY_CACHE_DATAFUSION_MAX_SIZE`, 1536+1536 MB) alone approach 1.5x of the new request and the memory caches compete with ingest for the same limit (FSTree landmine above); 7Gi keeps the burst headroom.

## Sizing: the memtable/intervals evidence (cmdshift/platform#171)

First config burned **~830m sustained CPU** — bursty zstd dump/merge across all cores + 60s compaction cycles. Full decision tables live in the values files' README rows above; the historical evidence:

- **Memtable 768MB + 4Gi limit**: the default derives 25% of container mem_total (256MB at 1Gi) and ~1400 streams overflowed it on the first scrape cycle (`MemoryTableOverflowError` 503s); 256MB still overflowed at ~150/min. 768 + the 4Gi limit holds the working set with the thread caps.
- **Thread caps 2** (dump/move/merge) + **halved intervals** (retention 30s, file-push 60s, compact-interval 150s): doubling the frequency means smaller units of zstd/merge work — bursts cool between them instead of one core pinned for long stretches.
- **Query caches capped** (memory-cache 512, datafusion 256 — they compete with ingest for the same limit); **disk cache OFF** (duplicates rustfs reads, burns CPU on GC).
- Result: **~200m avg, 0 overflows, 100% 200s**. (The current shape supersedes these numbers — see the cmdshift/platform#182 bullet below; the sizing evidence lives in the values decision tables.)
- **Compaction is ON** (cmdshift/platform#182): an earlier "tuning" left `ZO_COMPACT_ENABLED` false, which silently disabled data retention entirely (retention lives inside the compactor module). Current shape: compact enabled, interval 600s, batch 50, fast-mode false, retention 10d (#186 — disk-gated bump from 3d, see the landmine above), `ZO_MAX_FILE_SIZE_ON_DISK: "16"`. The interval rides 600s (the values file's setting — the #182 "60s" wording here was stale against the live config); the #171 60s-cycle burn history is what argues against going BELOW it — the work set is now bounded by 10d retention; post-change openobserve sits ~120m CPU, well under the 2-core limit.

## openobserve pod churn: graceful replacement only

**Never force-delete the openobserve pod or live-patch it** — four occurrences had the same shape (cmdshift/platform#171; upstream openobserve/openobserve#14590): an ungraceful pod replacement (helm upgrade → new checksum → SIGKILL) killed SQLite mid-write; every restart replayed the dirty WAL and failed `stream cache failed: disk I/O error (6410)` at ~2s after start. A debug-pod dd test proved the volume writes 250MB/s — corruption was WAL state, **not the disk**.

The "MANDATORY pod-churn procedure" (suspend → scale 0 → graceful delete → **delete the PVC** → scale up) is **RETIRED** — its root cause was the missing `/tmp` emptyDir, not the local-path PVC (O2 writes temp files there under `readOnlyRootFilesystem: true`; fixed in cmdshift/platform#209). Evidence: `openobserve-0` healthy 35h across 3 restarts with the fix in place, zero I/O errors. Normal pod churn (helm upgrade, requestedAt annotate, rollout) is fine as-is; the only standing rule is graceful replacement — never `--force`, never a live patch (flux owns the pod template; drift is fixed by changing the manifest and reconciling).

Metadata (users/dashboards/alerts) is disposable — it lives in Git via the openobserve-sync Job and re-syncs after any pod churn (cmdshift/platform#206; between the o2-sync removal and the restore it was genuinely unrecoverable, which is what the old export-before-churn dance was for). Data itself survives in rustfs.

## Credentials: secret-driven (cmdshift/platform#209)

The O2 root credential lives in exactly one place — the secrets-server payload `observability/openobserve-credentials` (`cluster/local/secrets/locals.tf`). Three derived keys share it:

- `ZO_ROOT_USER_EMAIL` / `ZO_ROOT_USER_PASSWORD` — the O2 root user (chart's `auth.existingRootUserSecret`).
- `O2_AUTH_BASIC` — `Basic + base64(email:password)`, **computed in terraform from the same locals** (never hand-typed; a credential change re-derives it on the next apply).

The `openobserve-credentials` ExternalSecret uses `dataFrom: extract`, so new payload keys appear in the k8s secret automatically (1m refresh) — no manifest change needed. Consumers:

- **Collectors** (agent + gateway): `extraEnvs` injects `O2_AUTH_BASIC` from the secret; the otlphttp exporter headers expand `${env:O2_AUTH_BASIC}` at collector startup. A credential change needs only a collector rollout restart — no values re-encoding, no CM-digest dance (the old inlined-header 401 trap is dead).
- **`prometheus_query` / `log_query`**: read the same key live from `secret/openobserve-credentials` (cache + 401-refetch-once).

## openobserve-sync: restored (2026-11-12, cmdshift/platform#206)

The **`openobserve-sync` Job** (`observability-config/openobserve-sync/`) GitOps-syncs alert destinations, stream manifests, dashboards, and alerts into O2 via REST — the ONLY GitOps path for them (OSS O2 has no CRDs/CLI/Terraform). Successor to the o2-sync Job removed 2026-10-29 (`5bb7c5a`): image `platform/openobserve-sync:default` (alpine+curl+jq, built by the restored `cluster/local/images/` module), script rides a configMapGenerator ConfigMap — script edits reconcile via flux only, no terraform round-trip. 18 detectors are live (watchdog heartbeat included; the flux pack adapted — see [Flux alerts](#flux-alerts-adapted-live-cmdshiftplatform182--206)); `trivy_critical_image_vulnerabilities` stays parked ([scanning README](../scanning/README.md)); no ServiceAccount (the old one was vestigial — zero refs, token mount already off); auth is env from `secret/openobserve-credentials` (`ZO_ROOT_USER_EMAIL`/`PASSWORD`).

Flow (POSIX sh, small named functions): destinations → **stream seeding** (existence-gated via `GET streams?type=<type>`; metrics via `ingest/metrics/_json`, logs via `/<stream>/_json`; the `up` stream is NEVER seeded — no fake `up=1` rows; entries may carry `"seed": "now"` for timestamp gauges like `velero_backup_last_successful_timestamp`) → **dashboards** (create-only by title: POST always creates, so the script re-fetches the list per file and creates if absent — UI-made edits win, Git edits after first creation do not propagate) → **alerts** (v2 API, existence-skip, bounded stream-retry before failing).

- The v2 alerts API path is `/api/v2/{org}/alerts` — **v2 nests BEFORE the org segment** (`/api/{org}/v2/alerts` 404s); list endpoints return `{"list":[…]}` wrappers.
- **O2 v1.0.1 list entries are dual-field**: dashboard list rows carry `dashboard_id` (snake) at entry level plus version-nested bodies (`v5` with camel `dashboardId`) — id-lookup jq must walk both shapes with nulls dropped (`(.dashboardId // .dashboard_id // empty)`); a lookup that misses makes POST duplicate dashboards (three created live before the fix, cmdshift/platform#206).
- **Re-run trigger is the configMapGenerator hash suffix** + `kustomize.toolkit.fluxcd.io/force: Enabled` on the Job: a completed Job never re-runs otherwise — any JSON/script edit changes a CM name → flux delete+recreates the Job → sync re-runs (traps: [observability-config README](../observability-config/README.md#openobserve-sync-traps-cmdshiftplatform206)).
- **Email destination schema**: one `email`-type destination, recipient `admin@cloud.test` (the O2 root user — implicitly an org member, which destination recipients must be).
- **Seed-value trap**: `velero_backup_last_successful_timestamp` must never seed 0 (reads as "last success at epoch 0") — its stream manifest carries `"seed": "now"` (current epoch), and the seed row has no schedule label so it can't match the alert's `{schedule="pvcs"}` selector. The gauge only materializes naturally after a FULLY successful backup — a PartiallyFailed nightly never emits it (cmdshift/platform#206).
- **hostmetrics series carry no node identity** (only `state`/`device`/`direction`), and the per-node agents' series are label-identical → O2 dedupes them to one arbitrary node: any per-node grouping/legend on `system_*` metrics is a lie. The `Kubernetes  / Nodes` dashboard's CPU%/Mem% panels therefore divide collector `k8s_node_{cpu,memory}_usage` (has `k8s_node_name`) by kube-state-metrics `kube_node_status_allocatable` — joining them needs a **`label_replace(…, "k8s_node_name", "$1", "node", "(.*)")` bridge** (ksm labels the node `node`; O2's PromQL supports it). The storage panels are deliberately cluster-wide totals (`sum(rate(…))`, static legends) — per-node disk needs a collector-side transform upserting node identity onto `system.*` (PARKED, cmdshift/platform#206; render-verified approach in the session ledger). (Cadvisor-sourced `container_fs_*` are the exception: they carry NATIVE `namespace`/`pod`/`node` labels, so the `Kubernetes  / Namespaces` disk panels filter/group `namespace`, not `k8s_namespace_name`.)

## otel collector: RBAC + opt-in metrics

- **kubeletstats with utilization metrics** needs `nodes/stats` + `nodes/proxy` + `nodes/pods` — without the proxy/pods pair the summary scrape 403s (`resource=nodes, subresource(s)=[pods proxy]`); the utilization metrics only derive from the `/pods` summary endpoint. The chart's `clusterRole.rules` **APPENDS to the preset rules** — add, don't replace.
- **apiserver `/metrics` scrape** needs `nonResourceURLs: [/metrics]` get (non-resource SAR — the kubelet-style rules don't cover it).
- **kubernetes_sd discovery** (the gateway's prometheus receiver) needs services/endpoints/endpointslices/pods/nodes/namespaces list+watch — the preset role only covers k8sattributes' pods; without it every scrape job resolves zero targets while the pod stays healthy.
- **Computed utilization metrics are OPT-IN** — stock presets ship them off: `system.cpu.utilization`/`system.memory.utilization` (hostmetrics receiver `metrics:` blocks), `k8s.pod.*_utilization` (kubeletstats `metrics:` block). The o2 community dashboards/alerts read them. `k8s_node_condition_ready` comes from the `k8s_cluster` receiver (clusterMetrics preset, **leader-elected in daemonset mode** so the replicas don't duplicate).

## valuesFrom staleness: the CM-digest trap

A values-ConfigMap-only change does **not** re-trigger helm-controller — the HR reconciles clean while `status.lastAttemptedConfigDigest` stays frozen at the old digest (the CM updated underneath it). Hit 4+ times during tuning. Verify:

```sh
kubectl get hr openobserve -o jsonpath='{.status.lastAttemptedConfigDigest}'
```

If it's stale after reconcile + requestedAt annotate (kubectl only — `flux annotate` doesn't exist; use `--overwrite` since the annotation carries a prior value), the fix is the suspend → `helm uninstall` → resume dance (or a full group bounce). When the pending rollout must not SIGKILL SQLite mid-write (openobserve itself), suspend FIRST, then annotate — the request is queued and processed on resume (cmdshift/platform#209 ran this successfully). `flux_triage` shows attempted-vs-applied revision lag to recognize the state; `helm_wait` for the per-release verdict. (The general ordering rule — `flux_wait` before `helm_wait` on values-only changes — lives in the `platform-workflow` skill.)

## ConfigMap size caps: two different limits

- **~256KB last-applied annotation cap (kustomize-controller)**: its client-side-apply dry-run embeds object content in `last-applied-configuration` — **not** the 1MiB CM data limit. A 420KB dashboard JSON alone failed the whole group's dry-run with a confusing Job error (cmdshift/platform#171). **Keep every generated CM well under ~250KB**.
- 1MiB CM data limit and the 1MB helm release-secret cap ([adopt-chart skill](../../../.agents/skills/adopt-chart/SKILL.md)) are separate checks — a CM can pass both and still fail the annotation cap.

## Alert patterns (O2 native detectors) — active (restored cmdshift/platform#206)

18 detectors are live, synced by the openobserve-sync Job (O2 → SMTP → mailpit delivery, `ZO_SMTP_*` env). New detector = JSON in `observability-config/openobserve-sync/alerts/` → CM hash re-triggers the Job. The evidence-based semantics the restored JSONs encode:

- **Any alert built on a gauge that materializes only after a first success needs an absent()/zero-guard arm** — `velero_backup_last_successful_timestamp` is absent before the first Completed backup (cmdshift/platform#111). Nuance discovered at restore: the gauge only emits after a FULLY successful backup — a PartiallyFailed nightly never writes it (seed `"now"` covers the gap; cmdshift/platform#206).
- **PartiallyFailed lives in the partial-failure counter, not the failure counter** — a rule watching only the failure counter is blind to exactly the failed-volume-data state it exists for.
- **One-shot counter spikes don't page**: sustained-condition windows (`for:` equivalents, `min_over_time` guards) absorb rebuild-time bursts (the tetragon bootstrap-kill flap, cmdshift/platform#60); a `increase(<counter>[window]) > 0` condition is safe against historical nonzero counters (only deltas fire — the un-parked `velero_repo_maintenance_failed` relies on this).
- Keep a **`watchdog` always-firing heartbeat** — its silence in mailpit is the one signal that survives a broken detector stack (cmdshift/platform#206; delivery verified live: O2 → SMTP → mailpit body-read 2026-11-12).
- **`gotk_resource_info` is GONE from the flux controllers** — v1.9.2 source-controller / v1.6.2 helm-controller (flux v2.7-era) no longer export it; upstream moved CR-state metrics to kube-state-metrics custom-resource-state config (`flux_resource_info`, fluxcd/flux2-monitoring-example#35). Never seed-fake a missing controller-native metric — check what the controllers actually export first, and re-point (the flux detectors read `controller_runtime_reconcile_total` now).

## Flux alerts: adapted, live (cmdshift/platform#182 → #206)

The `o2-alerts-library` fluxcd pack (3 of 4 adopted: `flux_helmrelease_failure`, `flux_kustomization_failure`, `flux_source_issue`) is synced into O2 again by the openobserve-sync Job — **adapted off `gotk_resource_info`, which the v2.7-era controllers (source v1.9.2 / helm v1.6.2) no longer export**: all three now read `increase(controller_runtime_reconcile_total{result="error"}[15m]) > 0` with a per-kind `controller` label regex (`helmrelease` / `kustomization` / `gitrepository|helmrepository|bucket|ocirepository`) — same not-ready semantics (reconcile errors in the window ≈ resource not-ready), and the series carries exactly those controller labels. If detector needs grow past reconcile errors, the upstream replacement is kube-state-metrics `flux_resource_info` via custom-resource-state config (fluxcd/flux2-monitoring-example#35). `flux_image_issue` stays PARKED — image automation controllers run `create: false` in this cluster, so its stream can never exist. Mechanics:

- **The `flux-controllers` gateway scrape job selects on `__meta_kubernetes_pod_label_app` regex alternation** — flux pod templates carry only `app: <controller-name>` (the `app.kubernetes.io/*` labels live on the Deployment, not the pod template), so pod-role SD can't use the standard label set. The metrics port is **named `http-prom`** (8080 is the http port). Verified live at the time: `gotk_resource_info` rows carried `service_name="flux-controllers"` for all four controllers (the metric itself died in the v2.7-era controllers — see the section intro).
- The pack is CC-BY-4.0 (awesome-prometheus-alerts): keep the source block verbatim in each JSON, and replace the broken upstream Go-template descriptions with operator guidance.

## quotas / limit-range / VPA

- `observability-config/logging.limit-range.yaml` sets Container defaults in `observability` — it exists for the **quota-vs-exception gap** (ResourceQuota admission is not skipped by kyverno PolicyExceptions; LimitRange is the only defaults source for exception-exempt containers). Mechanics: [runbooks/local/adding-a-workload.md](../../../runbooks/local/adding-a-workload.md).
- Two quotas: `compute` (32 pods) + the former `logging` quota renamed `logging-compute` (32 pods, converged from 36 on the 2026-11 re-audit — cmdshift/platform#186) — two `ResourceQuota/compute` objects in one namespace would both charge every pod (cmdshift/platform#120). A quota-exceeded ReplicaSet does NOT self-heal when the quota is raised — annotate the stuck RS (cmdshift/platform#155).
- All VPAs are **Off mode** — recommendations only, never mutation (cmdshift/platform#62). The chart runs the recommender only; `install.crds: Create` / `upgrade.crds: CreateReplace` because the CRDs ship in the chart's `crds/` dir (1MB cap a non-issue). Never run `helm test` on the vpa release — the chart renders three resource-less hook pods with no values knob; kyverno would deny them. Off-mode VPAs are hand-maintained (goldilocks removed) and coverage is **complete for every workload controller outside kube-system/flux-system** (cmdshift/platform#186 — the `vpa_recs` gap footer counts 0): a new workload gets one in its group manifest, `<controller>.vertical-pod-autoscaler.yaml` in the group's `-config` dir. kube-system/flux-system stay excluded **by design** — chart-pinned system plumbing, so the calibration table has no cilium/coredns rows there (cloud implication in [clusters/cloud/notes.md](../clusters/cloud/notes.md)).
