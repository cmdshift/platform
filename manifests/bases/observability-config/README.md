# observability-config

Local-config overlay for the [observability](../observability/README.md) group: the two namespace quotas, the LimitRange, the VPA object, and the **openobserve-sync Job** — the GitOps path for O2 dashboards/alerts/destinations (restored as the successor to the removed o2-sync Job; mechanics below, cmdshift/platform#206).

## Decision tables

### quotas + limit-range

| object | why | ref |
|---|---|---|
| `ResourceQuota/compute` (32 pods) | sized for the namespace pod set — shrank with the LGTM teardown (openobserve + collector replace loki/mimir/tempo/grafana/alloy/KSM/node-exporter). Realigned in cmdshift/platform#219 (openobserve 5120Mi→2Gi, gateway 256Mi→400Mi, agent 128Mi→144Mi, ksm 96Mi→48Mi): steady-state request sum ~2.9Gi (2928Mi), both quotas (10Gi requests.memory each) hold with ~70% headroom — re-verify the sums on any new workload in the namespace. Derivations: openobserve 7d P99 1562Mi × 1.2 = 1875Mi (VPA 1850Mi) → 2Gi; gateway 7d P99 329Mi × 1.2 = 395Mi (VPA 392Mi) → 400Mi, cpu live 5–16m (VPA 23m) → 25m; agent VPA 63m/138Mi, 7d per-pod P99 89–106Mi → 64m/144Mi; ksm 7d P99 35Mi × 1.2 = 42Mi (VPA 47Mi) → 48Mi, limit 144Mi keeps series-growth headroom (12h-era max 79Mi) | cmdshift/platform#171, cmdshift/platform#186, cmdshift/platform#219 |
| `ResourceQuota/logging-compute` (32 pods) | was `ResourceQuota/compute` in the logging namespace — renamed on the cmdshift/platform#120 merge: two same-named quotas would double-charge every pod; both admit every pod here, so each must clear the FULL namespace pod set; kept in lockstep with `compute` (lockstep history: cmdshift/platform#83, cmdshift/platform#128, cmdshift/platform#146) — its 36 pod cap survived the cmdshift/platform#171 shrink and let the pair drift; converged to 32 on the re-audit (cmdshift/platform#186, effective cap was already 32) | cmdshift/platform#120 |
| `LimitRange/compute-defaults` | quota admission fails any container lacking requests/limits — including PolicyException-exempt ones (wedged the (removed) thanos-ruler STS once, cmdshift/platform#111); these defaults fill that gap (sized from the config-reloader audit) | cmdshift/platform#111 |
| Two quotas, never folded | two `ResourceQuota/compute` objects in one namespace would both charge every pod | cmdshift/platform#120 |

## openobserve-sync traps (cmdshift/platform#206)

- **Re-run trigger is the configMapGenerator hash suffix** + `kustomize.toolkit.fluxcd.io/force: Enabled` on the Job: a completed Job is never re-run otherwise — any dashboard/alert/script/streams edit changes a CM name → Job deleted+recreated → sync re-runs (cmdshift/platform#171). **`dryrun_check` cannot validate a changed Job pod template** (field is immutable — kubectl server dry-run fails with "field is immutable"); the force annotation's delete+recreate IS the designed mechanism, so a dryrun_check immutable-Job failure on this Job is expected noise, not a gate failure (verified landing at flux_wait, cmdshift/platform#206).
- **Dashboards grouped by domain into separate configMapGenerator entries** (script/streams/dashboards/destinations/alerts, plus `openobserve-sync-dashboards-overview` since cmdshift/platform#218) — each generated CM has its own ~256KB cap in the kustomize-controller dry-run (last-applied annotation, not the 1MiB data limit); `kubernetes-overview.json` alone (420KB) was dropped for it (cmdshift/platform#171) and now ships through its own `openobserve-sync-dashboards-overview` CM, mounted at a NESTED `/dashboards/overview` volumeMount — `sync.sh` enumerates dashboards with a recursive `find /dashboards`, so the second CM needed no script change (cmdshift/platform#218). Cap-math precedent from that landing: the minified overview (237,258 B) JSON-escapes to ≈260.6KB in the last-applied annotation vs the 262,144-byte cap — a marginal pass with ~1KB headroom held; `dryrun_check` (the server dry-run) is the authoritative verdict, not the byte estimate. Keep the split as the alert set and dashboard count grow.
- **Dashboards are create-only by title: a Git edit to an EXISTING dashboard never propagates** (the sync skips on title, UI edits win). To make Git win: DELETE the dashboard via the O2 REST API (`DELETE /api/{org}/dashboards/{dashboard_id}` — take the id from the GET list by exact title) BEFORE the reconcile, so the CM-hash-retriggered Job finds the title absent and re-creates it from Git; dashboards are Git-owned metadata (disposable on pod churn), so the delete is safe (cmdshift/platform#217 — used to land the per-node `Kubernetes  / Nodes` revert).
- **Alerts are create-only by name too**: `sync_alerts` skips an existing name, so a Git edit to an existing alert JSON never propagates — `DELETE /api/v2/default/alerts/{alert_id}` (id from the `{"list":[…]}` GET by exact name) **before** the edited JSON reaches the bucket (the sync container mirrors within seconds), then the CM-hash-retriggered Job re-creates it from Git and O2 evaluates it immediately. The sync stops at the first alert whose stream never appears (`exit 1`), so pre-check streams (cmdshift/platform#231).
- **Streams that only materialize on their first event abort a rebuild's re-seed** (hit live): `kube_pod_container_status_waiting_reason` (CrashLoopBackOff), `kube_pod_container_status_terminated_reason` (OOMKilled), `kube_job_failed` (a failed Job must exist for ksm to emit it) and `velero_repo_maintenance_failure_total` (velero registers the counter only after the first maintenance failure) don't exist in a freshly rebuilt O2 — the sync Job creates alerts in glob order and dies with `404 Stream … not found` → BackoffLimitExceeded, leaving every later-alphabet alert absent and `observability-config`'s health check red. Fix: `streams/lazily-materialized-streams.json` seeds all four as 0-gauges (0 never matches a reason/reason-filtered alert). After any O2 PVC rebuild: expect the first post-rebuild sync Job run to surface any NEW missing stream the same way — add it to that seed file rather than hand-seeding in O2. Artifact-freshness reminder: `sync_wait` proves bucket parity, not the source artifact — `flux reconcile source bucket main` before `flux_wait` when a fix must land now (the second Job run failed on the stale artifact before the forced refresh).
- **O2 dashboard JSON traps**: every panel query's `fields.stream` must be a non-null STRING — `"stream": null` fails the whole POST with 422 `invalid type: null, expected a string` (two Error'd Job pods before diagnosis, cmdshift/platform#206); pure-promql queries still name their primary metric there. GET-by-id returns a version-nested body — the dashboard lives under `.v5` (top-level `.title`/`.dashboardId` are null), while the list wraps in `{"dashboards":[…]}` (alerts use `{"list":[…]}`).
- **The `Kubernetes / Events` dashboard + `k8s_events` seed (cmdshift/platform#218)**: the events dashboard joins the existing `openobserve-sync-dashboards` CM (12 files now); `streams/kubernetes-events.json` seeds the stream — a benign existence-gate (the stream is normally already live from the gateway collector, and the Job log shows `stream exists: k8s_events`), there for O2-rebuild recovery. **Events posture: the stream is fed by the gateway's real-time `events.k8s.io` watch — no historical backfill, events during gateway downtime are lost, watch starts at the current resource version** (mechanics: [observability README](../observability/README.md) gateway decision table). The stream's `severity` column carries the raw k8s event-type values `Normal`/`Warning`.
- **The overview's two `_o2_service_graph`-referencing panels are DROPPED** (cmdshift/platform#218): "Custom Resource Definitions" (Panel_ID6551210) and "VPAs" (Panel_ID8517410) — no traces emitter exists (beyla removed) and a CRD-object watch is out of scope, so those panels would ghost regardless; the now-empty "Custom Resources" tab is dropped too, the "Extra" tab keeps its other 2 panels. The unrelated "CRDs" panel on the Overview tab (a kube_* metric counter) stays. Re-adapt only if a traces emitter (or a CRD-watch source for the dashboards) ever shows up.
- **The Job runs after the group's workloads** — the sync Job curls the O2 API, so openobserve must be ingesting first; the `observability-config` kustomization dependsOn the observability group.
- **Stream-manifest pattern**: each dashboard ships a `streams/<name>.json` — a JSON array of `{"stream": "<name>", "type": "metrics"|"logs"}`; the script existence-gates each entry via `GET streams?type=<type>` and seeds only the missing (metrics via `ingest/metrics/_json` value 0; logs via `/<stream>/_json`). **The `up` stream is never seeded** (no fake `up=1` rows). **Seed-value trap**: a timestamp gauge must never seed 0 — `velero_backup_last_successful_timestamp`'s entry carries `"seed": "now"` (current epoch; seed rows carry no schedule label so they can't match a selector).
- **No ServiceAccount**: the old o2-sync SA was vestigial (`automountServiceAccountToken: false`, zero RBAC/NetworkPolicy refs) — the Job keeps `automountServiceAccountToken: false` but no SA; auth rides env from `secret/openobserve-credentials`.
- **kyverno `deny-shell-entrypoint` catches an explicit shell in `command`** (`["/bin/sh", "/script/sync.sh"]` fails admission) — use direct script exec `["/script/sync.sh"]` (CM file defaultMode 0555, shebang interprets; container-init execs escape pod-scoped tetragon). The scanning group's `allow-trivy-scan-jobs` is the documented exception.
- **`dryrun_check` fails any braced `${VAR}` token in the embedded script** (postBuild-token false positive — flux only substitutes declared vars, so `$VAR` and `${VAR}` reconcile identically); write embedded shell unbraced (`AUTH="$O2_USER:$O2_PASS"`).
- **O2 v1.0.1 dual-field naming**: dashboard list entries carry `dashboard_id` (snake) at entry level plus version-nested bodies (`v5` with camel `dashboardId`) — the id-lookup jq walks both (`(.dashboardId // .dashboard_id // empty)`); a lookup that misses makes the create-only POST duplicate dashboards (three created live before the fix, cmdshift/platform#206).
- **Parked alerts** (inventory, not rationale): `trivy_critical_image_vulnerabilities` stays out — its stream (`trivy_image_vulnerabilities`) materializes only after the first VulnerabilityReport, none exist (vuln-scan investigation parked; [scanning README](../scanning/README.md)). `velero_repo_maintenance_failed` is no longer parked — restored with `enabled: true` (its failure_total stream exists; the `increase(...[2h])` condition can't fire on historical nonzero counters, cmdshift/platform#206).
