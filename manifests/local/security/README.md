# security

Tetragon (runtime, eBPF) + trivy-operator (static posture) + `security-config/` (TracingPolicies, vendored compliance specs, PolicyException). Episodic kube-bench runs are temp scaffolding, not committed manifests. All three replaced platform-wide posture scanning (kubescape: adopted and removed same day — too heavy for what it delivered; its NSA hardening settings survive in the manifests).

## Kernel intel (check the kernel before adopting anything in this class)

The kernel is the host's on every shape: macOS/Docker Desktop hosts run the linuxkit **7.0.12** VM kernel (the bullets below were verified there); Linux/Docker Engine hosts run the host kernel directly — **7.2.4-arch1-2** on the Arch workstation. Kernel-7.2 findings are flagged where they bite (cilium: [networking/README.md](../networking/README.md); tetragon: below). Check the kernel before adopting any tool in this class — the cost of not doing it is a startup-dead DaemonSet on every node. Node-targeted talosctl commands need an explicit `-n <node-ip>` (the talosconfig context sets no default node; `talosctl config get-contexts` shows the gap, kubectl `get nodes -o wide` the IPs):

- **fanotify permission events are unavailable** (`CONFIG_FANOTIFY_ACCESS_PERMISSIONS=n`, `docker run alpine zcat /proc/config.gz`) — killed the kubescape node-agent's container watcher at startup on every node; the init is unconditional, so no partial-enable workaround. This killed kubescape (cmdshift/platform#24).
- **eBPF tools are proven viable**: `CONFIG_DEBUG_INFO_BTF=y` (+ `/sys/kernel/btf/vmlinux`), `KPROBES`/`KPROBE_EVENTS`, `FTRACE_SYSCALLS`, `TRACEPOINTS` — verify via `talosctl -n <node> read /proc/config.gz | zcat | grep BTF` (no extra container needed).
- **`CONFIG_BPF_LSM=y` is not proof of LSM-hook support**: the vmlinux BTF lacks `bpf_lsm_*` hook symbols, so `lsmhooks:` policies fail to load ("lsm hook security_file_open not found in BTF"). Ritual: `talosctl -n <node> read /proc/kallsyms | grep -wE "[Tt] (<symbols>)"` **before** writing the policy, then `cr_validate` before `sync_wait`. Plain kprobes on the same symbols work, and `fmodret: true` is supported, so Override stays available via kprobes. Inlined symbols (`free_module`) don't attach; local `t` symbols (`do_init_module`) do.

## Tetragon

- Release `tetragon.helm-release.yaml` (chart 1.7.1, same `cilium` HelmRepository as cilium — no new source); PSS `privileged` on the `security` namespace; PolicyException in `policies-config/` (agent runs privileged with host paths `/proc`, `/sys/fs/bpf`, `/sys/kernel/tracing` — the Talos ≥1.12 tracefs requirement, which in Talos-in-Docker **container mode** additionally needs the `mount-tracefs` init container below); CNP in `networking-config/`. TracingPolicy CRDs are operator-managed (`crds.installMethod: operator`) — tiny release, no hook jobs, no 1MB-secret risk.
- **Tracefs mount for Talos-in-Docker container mode** (postRenderers kustomize patch on the DaemonSet — helm stays the single writer): machined mounts `/sys` fresh in container mode and skips the pseudo-fs submounts (MountPseudoLate runs only in `!container`), so `/sys/kernel/tracing` is an unmounted sysfs dir — the agent's own auto-mount refuses to mount over the kubelet's hostPath bind ("instance exists with other type"; mountinfo shows sysfs, not tracefs) and cilium/ebpf's kprobe attach dies with "neither debugfs nor tracefs are mounted". The patch adds a privileged `busybox:1.37` init container `mount-tracefs` that mounts tracefs **only if the fstype check says it isn't tracefs already** (`stat -f -c %t /sys/kernel/tracing` = `74726163` → no-op), with `mountPropagation: Bidirectional` on both the init container's and the agent's volumeMounts so the mount propagates up to the node's `/sys` and back down into the agent's bind. The guard makes the patch a no-op wherever tracefs is already mounted (real Talos in the cloud — remove-in-the-cloud candidate, [manifests/cloud/notes.md](../../cloud/notes.md)); admission is covered by the `allow-tetragon-security-contexts` PolicyException (name-prefix match, cmdshift/platform#80).
- **Stage-1 observe policies** (`security-config/*.tracing-policy.yaml`, all monitor_only): kernel-modules, privileges-raise, bpf-activity, sensitive-host-paths. Alert rules in `monitoring-config/thanos-rules.yaml` (`tetragon-alerts` group).
- **Policies MUST carry a `podSelector`**: per-hook `matchNamespaces Pid NotIn host_ns` did NOT exclude host processes live (runc's container-setup setuid calls kept firing) — the working "k8s pods only" filter is the policy-level podSelector (sensors then show a non-zero FILTERID). Worse: policies **without** a podSelector don't reach the export sink at all while `enable-policy-filter: true` (tetra gRPC sees everything regardless). The selector is also the enforcement scope — see the exec deny-list bullets for label-scoping patterns.
- **Stage-2 flips are manifest edits** (`spec.options`), never `tetra tp set-mode` — flux is the source of truth. Flip 1 (kernel-modules → enforce, Override(EACCES) on `security_kernel_module_request` + Sigkill on `do_init_module`/`security_kernel_read_file(READING_MODULE)`) shipped with burn-in evidence (cmdshift/platform#28): Override-on-request exists because every Go runtime's first socket() probes missing modules — a strict Sigkill would murder arbitrary controllers; Talos denies `CAP_SYS_MODULE` to containers, so the Sigkill path is armed but unreachable from pods. **Kernel-7.2 caveat on that hook**: the kernel rejects kprobe_multi attach for Override actions on `security_kernel_module_request`, so the agent carries `extraArgs.disable-kprobe-multi: "true"` in `tetragon-values.yaml` (upstream hint: `--disable-kprobe-multi`) — a host-kernel workaround to re-verify if the cloud nodes' kernel attaches kprobe_multi cleanly. Flip 2 (exec deny-list, `exec-deny-list-{flux-system,policies,secrets}` → enforce/Sigkill on `security_bprm_check`) shipped straight from static evidence (cmdshift/platform#28): every container in the three namespaces runs its image entrypoint directly, no CronJobs, bootstrap "hooks" are annotations not Jobs — nothing legit execs shells at steady state or rebuild. Verified per policy with a labeled busybox probe (`kubectl exec` of `/bin/sh` → exit 137); per-node NENFORCE summed to exactly the probe kills (the collateral-check ritual for any future flip: no 137 exits + NENFORCE == probe count exonerates the policy). Flip-3 gates (sensitive-host-paths override) are tracked in the issue — 1-day watch on flips 1+2 first.
- **Exec deny-list landmines** (each cost a debugging round):
  - `arg type: file` on `security_bprm_check` passes `cr_validate` (schema-valid) and the agent logs only a load-time **validation warning** ("type (struct linux_binprm *) does not match spec type (file)") while the policy silently never enforces — `type: linux_binprm` is the working type. After loading any new kprobe policy, grep agent logs for `validation warning` and check NENFORCE > 0 with a live probe.
  - The 1.7.1 CRD names the Override error field `argError` (the docs' `errno` is newer naming) — `errno` fails `cr_validate` with `unknown field`.
  - **The 1.7.1 CRD has no `Kube` namespace matcher** (`matchNamespaces` supports kernel NS types only; `matchWorkloads` with the `k8s:io.kubernetes.pod.namespace` expression exists upstream but not in this CRD) — namespace scoping is per-policy `podSelector` over pod labels: flux-system pods carry only `app=<controller>` (list is explicit; a future flux controller must be added to come into scope), kyverno/external-secrets pods match their `app.kubernetes.io/instance` release label. Three policies, one per namespace, for exact kill-event attribution.
  - **Container-init execs escape pod-scoped enforcement** (empirically verified): the pod context isn't resolved yet when a container's entrypoint execs, so a shell-entrypoint container starts unharmed; post-init execs (kubectl exec, controller children) are killed. Image-based threats are trivy/kyverno's surface, not this policy's.
  - `linux_binprm` matching uses the **requested** path — busybox `/bin/sh` (symlink to `/bin/busybox`) still matches `/bin/sh`; no resolved-path entries needed.
  - `kubectl exec … sh` debug shells in the three namespaces are killed by design — diagnose via the observability stack or a temporary `policy-mode: monitor` flip.
- **Kill-event visibility** (cmdshift/platform#57 — each fact verified live):
  - **`tetragon_kill_events_total` does not exist** — not in v1.7.1, not in any tag, not in upstream's metrics reference. The alert now uses `tetragon_policy_events_total{policy=~"kernel-modules|exec-deny-list-.*"}` (materializes on the first enforcement event; empty labels don't matter to the expression). The 1.8.0 bump (cmdshift/platform#59) upgrades this to `tetragon_tracingpolicy_selector_actions_total{action=~"signal|override"}` — BPF-side per-selector action counters, landed upstream 2026-06-30 (`0b1125d2a`) but in no release yet.
  - **bprm_check enforcement events are pod-less by design**: the hook fires pre-exec, so the event is attributed to the pre-exec fork record (runc's child) with `process.pod=nil`/namespace `""` — the init-exec gap applies to attribution, not just enforcement. Consequences: the exporter denylist (`{"namespace":["", "cilium", "kube-system"]}`, chart default) drops them from Loki forever; `tetragon_policy_events_total` counts them with empty labels. Do NOT remove `""` from the exporter denylist to "fix" this — it would flood Loki with all host-side process activity.
  - **tetra compact renders them as `❓ syscall <node> /usr/bin/runc security_bprm_check`** (attributed to runc, node prefix instead of ns/pod) — easy to misread as unrelated runc noise. Use `tetra getevents -o json` to see the full event (`policy_name`, `action`, `args[0].linux_binprm_arg.path` = the denied binary).
  - The enforcement-verified ritual is unchanged: `kubectl exec … /bin/sh` → exit 137, per-node NENFORCE == probe count. The denied exec itself shows in normal exec/exit tracking as `/bin/sh` exit 137 (the process dies after the match).
- Option-value trap: `policy-mode` is `enforce`/`monitor` (upstream `TpStringToMode`) — `enforcement`/`monitor_only` fail agent-side with a load_error on every node while flux apply "succeeds". `spec.options` is a **list of `{name, value}`**, not a map — the on-cluster CRD schema settles both.
- Agent sizing is burn-in-audited (request 640Mi / limit 960Mi; memory is a warmup ramp then GC sawtooth, data cache capacity-bounded — evidence at the value in `tetragon-values.yaml`).
- **tetra access**: gRPC binds node loopback (`tetragon.grpc.address: localhost:54321`) — `kubectl -n security port-forward ds/tetragon 54321:54321` then `tetra --server-address localhost:54321 ...`; nothing exposed on the node IP. Subcommand is `getevents` (no `events`, no `--policy` filter in 1.7 — grep the compact output). See the observability skill for the exporter-labels gotcha.

## trivy-operator

- Chart `aqua/trivy-operator` — the docs site the URL points at is v0.3.0-era; **read the chart's values.yaml instead** (schema-less chart: `helm template` doesn't reject key typos). Values live in `trivy-values.yaml` via configMapGenerator → `valuesFrom`; the release spec itself stays minimal.
- **Values-key traps (silently ignored)**: operator pod resources are top-level `resources`, not `operator.resources`; `scanJobsConcurrentLimit`/`scanJobTTL` are `operator.` keys, not `trivyOperator.`. Caught only by inspecting the render.
- **Scan-job admission trap** (operator-generated pods are kyverno-checked): the operator hardcodes an empty pod-level securityContext — without `trivyOperator.scanJobPodTemplate*` values every scan job is denied and scanning **silently never runs**. `runAsUser: 65534` is load-bearing (image declares `USER root`; bare `runAsNonRoot` fails the kubelet image-USER check). Scan-job sizing must cover the **worst image in the fleet** (pods mirror the target's container list) — bumped to 512Mi/768Mi from OOM evidence, verified by forced rescan.
- **Built-in trivy-server** (`operator.builtInTrivyServer`): StatefulSet + local-path PVC caching trivy-db/java-db so scan jobs hit `trivy-service:4954` instead of downloading ~75MB of DB each (the values comment saying 4975 is stale).
- `scanJobTTL: 10m` TTL-deletes completed jobs. **Failed scans never requeue**: an OOMKilled/failed scan job is TTL-deleted, the 120h report cache blocks rescan, and the controller resync does not recreate failed scans — force a rescan by deleting any one **sibling** VulnerabilityReport of that workload.
- CIS compliance spec + infra assessment are **off on purpose** (node-collector jobs mount standard-Linux paths — Talos is neither, hostPath mounts would be admission-denied); NSA + PSS baseline/restricted specs are **vendored as CRs in `security-config/`** — re-vendor deliberately on chart bumps.
- `ignoreUnfixed: false` — full picture on purpose; the `TrivyCriticalImageVulnerabilities` alert (warning severity, Critical-only, platform namespaces) is informational and hardened against rescan-gap flaps with `max_over_time(...[30m])` (cmdshift/platform#36).
- **All pull paths run through the caching registry — and under the wildcard node mirror (`skipFallback: true`) that is mandatory, not just cheaper**: any registry not in the angos upstream map now **hard-fails at image pull** (no silent direct-pull fallback); the fix is a `registry_map` entry in `cluster/local/registry/locals.tf` + `terraform apply` (mechanics: [runbooks/local/cluster-rebuild.md](../../../runbooks/local/cluster-rebuild.md)). `mirror.gcr.io` (chart default) isn't in the map: tool images → `image.registry`/`trivy.image.registry: docker.io`; scan-job targets → `trivy.registry.mirror` string-rewrite (`ghcr.io/x` → `registry.cloud.test/ghcr/x`; `index.docker.io` normalized form — both prefixes); server DB → `dbRegistry: registry.cloud.test` + `dbRepository: docker/aquasec/trivy-db`. Mapped ≠ working: reg.kyverno.io's pull-through fails silently (404) — kyverno overrides to ghcr.io (rationale in `policies/kyverno-values.yaml`). The cache is plain HTTP via haproxy — `trivy.insecureRegistries` and `operator.builtInServerRegistryInsecure` are load-bearing.
- **Cold-start race on fresh rebuild** (expected, self-healing except the status-less ClusterSbomReport): [runbooks/local/cluster-rebuild.md](../../../runbooks/local/cluster-rebuild.md).
- valuesFrom gotcha: changing the values ConfigMap does not re-trigger the HelmRelease — `flux reconcile helmrelease trivy-operator -n security --with-source` after values-only edits (cmdshift/platform#31 pattern).

## kube-bench (episodic, not committed)

One-shot CIS benchmark as temp scaffolding (namespace `kube-bench-scan` with privileged PSS + scoped PolicyException + temp CNP, delete-ns cleanup) — spec lives in `cluster/local/.tmp/kube-bench-scan/`, run via `tools/bin/bench`. Pin the benchmark explicitly (kube-bench releases lag k8s; cluster is 1.36.4 → cis-1.12 is the closest released set).

**Talos intel for any future hostPath-mounted tool** (each cost a debugging round):

- **The kubelet's rootfs is curated** — `/var/lib/etcd` is invisible to hostPath mounts even though machined sees it (`hostPath type check failed: is not a directory`). Node checks can only cover paths kubelet itself needs (`/etc/kubernetes`, `/var/lib/kubelet`).
- **Control-plane static pod manifests are served, not stored** (`staticPodURL`) — `/etc/kubernetes/manifests/` on disk is empty. Remap trick: dump apiserver/controller-manager/scheduler specs via `kubectl get pod -o yaml` into an emptyDir mounted at `/etc/kubernetes/manifests`; etcd stays uncovered (machined service, not a pod).
- **Nested mounts need a writable parent** — a hostPath File inside a ro hostPath Directory fails at runc; use emptyDir parent + ro hostPath children.
- The kube-bench image ships sh + kubectl + busybox — one container, no initContainer needed; kubectl audits use `KUBECONFIG` (mount the admin kubeconfig as a Secret; its server is `127.0.0.1:6443` — the pod loopback — so `tools/bin/bench` rewrites it to `kubernetes.default.svc:443` when staging the Secret, and the temp CNP egress rule is the house `kube-apiserver` entity).

Triage ledger from the first run (zero true-positive FAILs; the rest is benchmark-vs-Talos layout mismatch): 1.2.30 `--service-account-extend-token-expiration` unset; 1.3.7/1.4.2 scheduler + controller-manager `--bind-address=0.0.0.0`; 4.3.1 kube-proxy metrics on 0.0.0.0; 1.2.5 `--kubelet-certificate-authority` absent (Talos-managed trust path). The `--authorization-config` file form (verified `Node, RBAC`) is where cis-1.12 expects the legacy flag; perms FAILs were podspec-dump emptyDir artifacts. Cloud re-verify: the layout noise mostly disappears on real nodes — see [manifests/cloud/notes.md](../../cloud/notes.md).
