In-repo markers (`# true in the cloud`, `# remove in the cloud`) flag these at the value; this file is the list with rationale. ## Hardening baseline + accepted deviations (NSA audit 2026-09-05; kubescape removed 2026-09-06)

Posture was driven by a kubescape NSA scan (baseline 80 → **92.3, zero failing controls** at removal; C-0069/C-0070 `notEvaluated` was the lean ceiling). The kubescape operator + `nsa_scan` were removed 2026-09-06 — too heavy for what they delivered; single-purpose hardening tools are the replacement (section below). The hardening settings it drove stay in the manifests as `# NSA hardening:` comments. This section is the deviations ledger those tools audit against — keep it current when adding workloads. Every deviation maps to a kyverno PolicyException or an upstream/CRD limitation:

- **thanos CR-managed pods (query/compact/store/ruler)** — the `monitoring.thanos.io` CRDs expose no `automountServiceAccountToken` and no per-container securityContext, so SA-token automount and roFS stay open for them. Disabling automount via SA manifests was tried and **the operator recreates the SAs on every reconcile**, reverting the field — don't fight it. Pod-level runAsNonRoot + seccomp ARE set (the only knobs the CRD exposes).
- **thanos-ruler config-reloader** — operator-injected, no resource/securityContext knobs (existing PolicyException, ~18Mi).
- **seaweed `main-master`** — no roFS: the CR has no persistence knob for master and it writes its wal/segment files to `/data` on the container's root fs. filer/volume/s3 got roFS; filer and s3 keep a writable `/tmp` emptyDir (filer's gRPC socket, s3 temp files live there).
- **velero deployment** — the chart only exposes `securityContext` at POD level and renders it into its CRD-upgrade hook jobs too, where `allowPrivilegeEscalation` is not a legal pod field (SSA rejects it, helm upgrade fails — hit live). Its pod-level `runAsUser: 0` default is deliberate (the node-agent needs root), so container-level roFS / caps dropping is not reachable via values; only the aws-plugin initContainer is container-hardened.
- **loki / alloy keep their SA tokens**: loki's rules sidecar watches ConfigMaps via the API, alloy's `discovery.kubernetes` uses in-cluster config. Alloy also still runs as root (image declares no USER — covered by its PolicyException for the host-log mounts).
- **kubernetes/Talos defaults** — the `system:*` discovery/basic-user ClusterRoleBindings and `cluster-admin → system:masters` (the Talos admin credential group) are stock bootstrap, not manifest-owned. Talos-rendered statics (apiserver/controller-manager/scheduler, kube-proxy, coredns) likewise.
- **ConfigMap regex false positives** — findings on config keys (cilium-config, kyverno/logging CMs) are verified non-credentials (policy strings look like secrets but aren't).
- **metrics-server** — the fix-first success: its `securityContext` value is container-level; `runAsGroup: 1000` in `metrics/` cleared the finding with no exception needed.

Hardening learnings worth keeping:

- **Explicit container-level `runAsGroup` is the common gap**: several charts set pod-level non-root or uid-only (gid implicit 0). Where the chart allowed it, explicit uid/gid is now set (cert-manager/eso/flux/lpp/ksm/grafana-op/seaweedfs-op — kills the implicit-gid-0 hole too); charts/CRDs that can't express it are covered by the deviations above.
- **flux2 chart securityContext REPLACES, not merges**: its templates hardcode container-sc defaults behind an if/else, so setting any value (e.g. just `runAsGroup`) silently drops APE/caps/roFS — spell out the full map (hit live; note in flux.helm-release.yaml).
- **thanos ruler non-root retrofit** needed `runAsUser: 65534` (numeric) at pod level, not just `runAsNonRoot: true`: the config-reloader image declares `USER "nobody"`, which kubelet can't verify against a bare `runAsNonRoot`. The PVC then needed a one-time `chown 65534` (helper pod pattern, same as seaweedfs) — the wal was root-owned from pre-hardening runs.

## Storage: `allowVolumeExpansion: false` on purpose (2026-09-06)

local-path-provisioner has **no volume-expansion support** — verified in the v0.0.37 source (only `create`/`delete` ActionTypes exist, zero resize/expand code), and non-CSI external provisioners can't expand regardless. The classes previously advertised `allowVolumeExpansion: true`, which the API accepts but nothing can ever act on: a PVC resize (e.g. a CNPG instance grow when `spec.storage.size` changes) would hang forever. Resize path locally = recreate the PVC at the larger size (velero FSB restore for data). The cloud's CSI StorageClasses expand natively — set `true` there (see `manifests/cloud/notes.md`).

## PVC volume stats arrived with the local PV conversion (2026-09-06)

`kubelet_volume_stats_*` (PVC capacity/usage — what dashboards and capacity alerts build on) only exists for volumes kubelet can stat, and **hostPath PVs are skipped** — a kubelet limitation, not a Talos one, though easy to misattribute on a Talos cluster where local-path is the provisioner. Before the 2026-09-05 conversion every PVC was hostPath-backed, so these series were silently absent. The StorageClasses' `defaultVolumeType: local` (added for velero FSB) plus the rebuild's fresh PVs made all 8 PVs `local`, and all 8 PVCs now report stats. Cloud note: if the cloud cluster ever provisions hostPath-style volumes, PVC metrics vanish the same way — dashboards/alerts on `kubelet_volume_stats_*` go quietly empty, no error anywhere.

## Loki retention + seaweed delete-path proof (2026-09-06)

Loki retention configured: `limits_config.retention_period: 30d`, `compactor.retention_enabled + delete_request_store: s3` (verified live in `/config`). ## Kubescape removed (2026-09-06)

The kubescape operator (namespace `kubescape`, release in `security/`, SecurityExceptions in `security-config/`) was removed — too heavy for what it delivered (3 Deployments + a scheduler CronJob scanning for drift the manifests already pin); single-purpose hardening tools are the replacement. Removal mechanics, for the record: exceptions + namespace + CRDs deleted **manually** — everything kubescape lived under `prune: false` (security-config, crds, namespaces) by design, and helm uninstall leaves the chart's 4 extra CRDs behind (helm never removes CRDs). Post-check: 25/25 kustomizations, 15/15 helmreleases, `policy_report` failures 0. The deviations ledger it fed survives in the section above; the cloud cluster gets the same tombstone in `manifests/cloud/notes.md` (don't resurrect it there).

**Kernel-limitation intel for the replacement tools** (from the kubescape node-agent's death, kept because it generalizes — attempted + reverted 2026-09-06): the Docker Desktop linuxkit 7.0.12 kernel hosting these Talos containers ships `CONFIG_FANOTIFY_ACCESS_PERMISSIONS=n` (`docker run alpine zcat /proc/config.gz`) — fanotify **permission events** fail `EINVAL`, which killed the node-agent's container watcher at startup on every node (with `RUNTIME_PATH` set correctly; Talos keeps runc at `/usr/bin/runc`, visible only via the `/host` mount). The watcher init is unconditional, so no partial-enable workaround exists. Cilium works because eBPF needs the BPF syscall + bpf fs — a different kernel feature. Before adopting any tool that needs LSM hooks (KubeArmor), fanotify permission events, or similar, check the linuxkit kernel config first; also budget its admission story (privileged DaemonSet → PolicyException + PSS labels).

Sync-container learnings from the same session (generic, kept): the sync container's inotify drops **edits** too, not just deletes (hit twice in one session, once producing helm upgrade/rollback churn against a stale artifact) — `rustfs cat <key> | grep <marker>` before `flux_wait` for edit-heavy sessions, and `docker restart sync-cloud-test` forces a full `--remove` re-mirror when the artifact hash won't move.

## Tetragon enabled (2026-09-07)

eBPF security observability — the first of the single-purpose hardening tools replacing kubescape. Release `security/tetragon.helm-release.yaml` (chart 1.7.1 — same `cilium` HelmRepository as the Cilium chart, no new source), namespace in `namespaces/security.namespace.yaml`, PolicyException in `security-config/`, CNP in `networking-config/security.cilium-network-policy.yaml`. TracingPolicy CRDs are **operator-managed** (`crds.installMethod: operator` default) — the rendered release is only ~18KB (no 1MB-secret risk) and there are **no hook jobs** (certgen only exists under gRPC-TLS cronJob; rthooks off). Observability-first: enforcement TracingPolicies are a deliberate follow-up — the linuxkit kernel has `CONFIG_BPF_LSM=y`, so enforcement is possible once the event stream has been watched for a while.

**Kernel verification closed the kubescape-intel question** (section above): linuxkit 7.0.12 has `CONFIG_DEBUG_INFO_BTF=y` (+ `/sys/kernel/btf/vmlinux` present), `KPROBES`/`KPROBE_EVENTS`, `FTRACE_SYSCALLS`, `TRACEPOINTS` — the agent loaded sensors cleanly on all 5 nodes (check via `talosctl read /proc/config.gz | zcat | grep BTF`, no extra container needed). The "check kernel config first" rule stands; eBPF tools are proven viable here, fanotify-permission-event tools are not.

**tetra CLI access** (CLI installed locally): `kubectl -n security port-forward ds/tetragon 54321:54321`, then `tetra --server-address localhost:54321 status | getevents | tracingpolicy ...`. The gRPC listener binds **node loopback** (`tetragon.grpc.address: localhost:54321`): kubectl port-forward dials 127.0.0.1 inside the pod netns, which for a hostNetwork pod is the node netns — so nothing is exposed on the node IP and the docs' unauthenticated-TCP warning doesn't apply. Subcommand is `getevents` (there is no `events`).

Accepted deviations: PSS `privileged` on the `security` namespace; `allow-tetragon-security-contexts` (security-config, prune:false) scoped to namespace + `tetragon` name prefix — the agent DaemonSet runs privileged with host paths (`/proc`, `/sys/fs/bpf`, `/sys/kernel/tracing` — the Talos ≥1.12 tracefs requirement) by design; chart default filters kube-system/`cilium`/host-namespace events from the export sink (gRPC output is unfiltered). Agent resources are provisional (50m/128Mi req → 1000m/512Mi lim) — audit after burn-in per the resource-sizing convention.

Landmine (cost a debugging round): `namespaces/` has an explicit `kustomization.yaml` resources list — a new `*.namespace.yaml` is **inert** until registered there. The `namespaces` kustomization applied "successfully" without it and every dependent waited on `namespaces "security" not found`.

## Tetragon enforcement stage 1 — observe (2026-09-07)

Four TracingPolicies in `security-config/` (all `monitor_only`, sensors confirmed via `tetra tracingpolicy list`): `kernel-modules` (module load/unload audit), `privileges-raise` (setuid/setgid-to-root family, capset, unprivileged userns — pod processes only), `bpf-activity` (bpf() loads + bpffs access — expected actors here are cilium/tetragon only), `sensitive-host-paths` (pod-side opens of `/var/lib/etcd` + containerd socket, rate-limited). Release gained `tetragon.enableProcessCred: true`. Alert rules in `monitoring-config/thanos-rules.yaml` (`tetragon-alerts` group) — `TetragonTracingPolicyLoadFailed` (fired for real during this session's load_error, resolved after fix) and `TetragonEnforcementKill` (arms itself at stage 2: `tetragon_kill_events_total` doesn't exist until the first enforcement event). `security-config/` is now `prune: true` (deliberate — flux = source of truth, retire by file deletion; the tetragon PolicyException moved to `policies-config/` with the other exceptions so it still lands before the release on a fresh rebuild).

**Kernel findings (linuxkit 7.0.12):**
- `CONFIG_LSM="yama,loadpin,safesetid,integrity,bpf,landlock"` + no `lsm=` cmdline override **looked** like full BPF-LSM support, but the vmlinux BTF **lacks the `bpf_lsm_*` hook symbols** — LSM-hook policies (`lsmhooks:`) fail to load with "lsm hook security_file_open not found in BTF". `CONFIG_BPF_LSM=y` in /proc/config.gz is not proof; check `talosctl read /proc/kallsyms | grep bpf_lsm_` before writing an `lsmhooks:` policy. Plain **kprobes on the same symbols work** (`security_file_open` attach confirmed live) and `fmodret: true` per agent feature-detection, so stage-2 `Override` stays available via kprobes.
- `free_module` is inlined in this kernel build (absent from kallsyms) — dropped from the modules policy; `do_init_module` exists as a local (`t`) symbol and attaches fine.
- Pre-flight ritual that works: `talosctl read /proc/kallsyms | grep -wE "[Tt] (<symbols>)"` **before** writing the policy, then `cr_validate` before `sync_wait`.

**Stage-2 plan (flips are manifest edits, not `tetra` runtime calls — flux is the source of truth):** kernel-modules → `Override + Sigkill` for non-host-PID-ns processes (modules-nohost pattern) first; then exec deny-list in `flux-system`/`kyverno`/`external-secrets` (block shells/interpreters/net-tools via `security_bprm_check` kprobe + namespace/binary selectors); then file-path overrides from sensitive-host-paths evidence. One policy at a time, each gated on a clean burn-in window.

**Open follow-ups** (tracked as cmdshift/platform#28 — burn-in audit + stage-2 ladder): re-audit tetragon agent resources after ~1 burn-in day (`cpu_audit`/`memory_audit` — `security_file_open` kprobe is hot; provisional 50m/128Mi req → 1000m/512Mi lim); bpf-activity logs a benign argument-type warning for `security_mmap_file` (upstream library uses `uint32` where the kernel takes `unsigned long` — display-only, kept for upstream diffability).

**Session landmines from this change (all cost debugging rounds):**
- **Dependency cycle**: putting the tetragon PolicyException AND the TracingPolicies in one group deadlocked both ways — the policies need CRDs the release's operator creates, while the release waited on the group for the exception. Rule: **CRs whose CRDs a release's operator creates must live in a group that `dependsOn` that release, never the reverse**; admission-critical exceptions go in the early group (`policies-config/`).
- **`wait: true` on conditionless CRs** (TracingPolicy has no status schema): the health check stalls the full `timeout` per attempt, and a stale discovery cache kept it failing with `no matches for kind` while the CRD demonstrably existed — 3 consecutive 2m timeouts for a group whose apply had succeeded. Fix: no `wait:true` on such groups; the health signal lives in agent metrics/alerts.
- **`lsm-kprobes`/`syscall` field names**: LSM policies use `spec.lsmhooks` with `hook:` (not `call:`) and no `syscall` key — both typos fail the root dry-run as "field not declared in schema". `cr_validate` catches these in seconds without the flux round-trip (the tool exists because of this session).
- **Sync drop, again**: a mid-session policy edit never reached the bucket while `sync_wait` claimed convergence (artifact revision hash frozen) — `docker restart sync-cloud-test` forced the full re-mirror. Verify with `rustfs cat <key> | shasum` against the local file when a revision hash won't move.
- **tetragon scoping**: per-hook `matchNamespaces Pid NotIn host_ns` did NOT exclude host processes live (runc's container-setup setuid calls kept firing). The working "k8s pods only" filter is the policy-level `podSelector: {matchLabels: {}}` — sensors then show a non-zero FILTERID and host-side noise disappears.

## Loosened flux polling for interactive determinism (2026-09-06)

Bucket `main` 1m → **5m**, root + child kustomizations 10m → **1h** (thanos-operator already 24h). Rationale: the intervals never gate change propagation (event-driven — artifact change requeues dependents at `retryInterval: 5s`), so the manual flow (`sync_wait` + `flux_wait --with-source`) is unaffected; what loosening buys is that background reconciles stop interleaving with interactive work — the 1m bucket poll could publish a half-mirrored artifact mid-edit (sync lag is documented) and the whole chain would start applying it. Drift-heal at 1h remains the enforcement of everything-in-files. Full manual (suspend) was rejected: a suspended tree reconciles nothing on rebuild, breaking the one-shot requirement. The bootstrap twins run 1m/10m until flux-config adopts and converges them — keeps fresh rebuilds fast. Cloud: keep the tighter 10m/1m there (multiple operators make frequent drift-heal worthwhile); see `manifests/cloud/notes.md`.

## Out-of-cluster companions (`*.cloud.test`)

rustfs S3, secrets server, haproxy, mailpit, sync container — terraform/docker in `cluster/local/external`; none of this exists in the cloud, so the CNP `toFQDNs` rules (`networking-config/*.cilium-network-policy.yaml`), the Bucket endpoint (`flux-config/main.bucket.yaml`), the ClusterSecretStore URL, alertmanager's mailpit smarthost, and velero's BSL `s3Url` all resolve differently there.

**Caching registry** (`registry-cloud-test`, `cluster/local/registry/`): angos pull-through cache at `registry.cloud.test` fronting docker.io, gcr.io, public.ecr.aws, registry.k8s.io, ghcr.io, quay.io, mcr.microsoft.com (`registry/locals.tf` upstream map). Every Talos node's containerd mirrors all of these through it (`nodes/templates/registry-mirror-config.tftpl.yaml` patch), so node-level image pulls never leave the docker network after first fetch. Two landmines:

- **The cache volume is not terraform-idempotent**: the `null_resource` in `registry/main.tf` runs `docker volume create platform-registry-data` only at CREATE (its trigger is a static string that never re-fires). If the volume is wiped (`docker system prune --volumes`, Docker Desktop reset), `terraform apply` will NOT recreate it — the registry container just starts with an empty `/data`. Fix by hand: `docker volume create platform-registry-data`, then re-apply (or `docker compose`-recreate the container). Full detail in `runbooks/local/cluster-rebuild.md`.
- **Chart defaults can bypass the cache**: any image from a registry outside the upstream map (e.g. trivy-operator's default `mirror.gcr.io`) pulls direct from the internet. Prefer chart image registries that the cache fronts (`docker.io`/`ghcr.io`/`registry.k8s.io`/`quay.io`) — done for trivy (2026-09-07), watch for it when adopting charts.

**Host → companion wedge (2026-09-07)**: `*.cloud.test` resolves to `127.0.10.1`, where Docker Desktop's port publisher listens (the only host path into the companion network — the 10.0.128.x vmnet is not host-routable). When that publisher path hangs, host curls to mail/secrets/s3 time out **while the cluster's own traffic still works** (velero/external-secrets kept hitting haproxy with 200s the whole time — check `docker logs cloud-test` before blaming the cluster). ## valuesFrom everywhere (2026-09-07)

All 17 HelmReleases now ship values via **configMapGenerator → `valuesFrom`** (issue cmdshift/platform#31; trivy was the 2026-09-07 pilot). Per release: values live in a plain `<release>-values.yaml` next to the HelmRelease, and the dir's `kustomization.yaml` generates `ConfigMap/<release>-values` (`valuesKey: values.yaml`). `prometheus-operator-crds` is the only release without values — untouched.

Conventions (the inline file comments were deliberately kept terse — this section is the canonical why):

- **`disableNameSuffixHash: true`, set per generator entry** (not a global `generatorOptions:`): `HelmRelease.valuesFrom` is not a kustomize-known name reference, so a content-hash suffix would desync the hand-written reference. helm-controller re-reconciles on configmap data changes anyway, so the hash buys nothing. Per-entry so a future generator that wants hashed names keeps them.
- **Every yaml in a dir must be registered in its `kustomization.yaml` `resources:`** — values files are the exception (generator inputs, not resources). An unregistered file is silently not built and flux prunes it from the cluster.
- **Rationale comments move with the values** (they were inline in `spec.values`); only local-only landmine notes stay inline.
- The `logging/`, `monitoring-config/`, `security/` kustomizations predate this and mix other generators (alloy config, thanos rules) — the values entries follow the same per-entry options style.

Tooling: `helm_verify` resolves `valuesFrom` refs locally (configMapGenerator entry first, literal ConfigMap fallback, unresolved = FAIL) and renders the exact values flux ships. `sync_wait` had a bug fixed this session: untracked files were excluded from its git-status collection, so newly-created manifests were never verified against the bucket (silent gap on add-style changes).

Cloud: adopt the same layout when refactoring `manifests/cloud/` — no local-only settings involved.

## thanos-operator upgraded — status conditions fixed + gated (2026-09-07, issue cmdshift/platform#22)

Upstream thanos-community/thanos-operator#636 (commit `831accd4`, main HEAD) replaced the sticky `ReconcileSuccess`/`ReconcileFailed` condition pair with a single **`Ready`** condition (True on success, False on failure) — the live CRs had both old conditions True simultaneously for hours before the fix. Bumped in lockstep: `manifests/sources/thanos-operator.git-repository.yaml` commit + image pin `main-2026-09-07-831accd` (the PR was Go-only; `bundle.yaml` diffed byte-identical between the two commits, so every kustomize patch re-verified unchanged).

**Conditions are now the health signal** — `monitoring-config.yaml` gates all four thanos CR kinds via `healthCheckExprs` on `Ready` True/False (same pattern as the Grafana/Alertmanager entries). Two semantics worth knowing:
- **Empty conditions pass vacuously** (`filter(...).all(...)` on `[]` is true): a CR the operator hasn't reconciled yet reads Ready. Same semantics the pre-existing entries always had.
- The **legacy `ReconcileSuccess`/`ReconcileFailed` conditions linger on the live CRs' status** (operator-owned status, not scrubbed — inert, the exprs only read `Ready`). A fresh rebuild produces only `Ready`.

**Condition failure/recovery proof** (worked example, status-only churn on a throwaway object): apply a scratch `ThanosStore` (`cond-test`) with real `objectStorageConfig` but **no `resourceRequirements`** → the operator's generated StatefulSet is denied at admission (kyverno `require-resource-limits` + `restrict-seccomp-strict`) → CR goes `Ready=False (ReconcileError)` within seconds; re-apply with resources+securityContext → `Ready=True (ReconcileComplete)` on the next sync (~5s); delete the CR → children cascade away. The CRD requires `spec.shardingStrategy` (apply fails without it). This is the recipe for verifying operator condition behavior on any future upgrade.

## Deployment dashboard — KSM v2 metric/label renames + PromQL join landmines (2026-09-07, issue #39)

`monitoring-config/platform-deployment.grafana-dashboard.yaml` is the first in-repo dashboard: the JSON lives in `platform-deployment.dashboard.json`, wired via `configMapGenerator` (`disableNameSuffixHash: true` — the CR name-references it) + `spec.configMapRef`; `url:` stays reserved for mirroring upstream dashboards. **The operator does NOT watch the ConfigMap**: JSON-only edits propagate on the dashboard's resync — `resyncPeriod: 5m` + `contentCacheDuration: "0s"` (a cached fetch served stale content once; the field is a string duration, not an integer). Metadata-only CR changes (annotations) are filtered out entirely — to propagate an edit immediately, bump any `spec` field. The log filter strip above the logs panel is a markdown text panel whose preset links set `var-log_filter` via URL while carrying `$namespace`/`$deployment`/`$__from`/`$__to` — Grafana pins variables to the toolbar, so a URL-param link is the only way to get a filter control mid-canvas. Authoring it surfaced Prometheus landmines that cost several debugging rounds; all verified live against kube-state-metrics v2.20:

- **KSM v2 metric rename**: `kube_pod_spec_volumes_persistent_volume_claims_info` (v1, still what most dashboards use) is **absent** — v2.20 emits `kube_pod_spec_volumes_persistentvolumeclaims_info` (no underscores). Same for any dashboard joining PVCs to pods.
- **`kube_replicaset_owner` has no `deployment` label** (v1 legacy) — the owner's name lives in `owner_name`. Deployment→pod mapping is therefore `kube_pod_owner{owner_kind="ReplicaSet"} * on(namespace, owner_name) group_left() label_replace(kube_replicaset_owner{owner_kind="Deployment", owner_name=~"$deployment"}, "owner_name", "$1", "replicaset", "(.+)")` — the label_replace overwrites `owner_name` (deployment name) with the RS name to make the join key line up.
- **Chained vector joins silently return empty**: `a * on(x) b * on(y) c` parses fine but matches nothing — the second `on()` group must be parenthesized: `a * on(x) b * on(y) (b2 * on(y) c)`. No error anywhere; the panel just renders empty. (Single-join chains are fine.)
- **`label_replace` label args must be quoted** (`"owner_name"`, not bare) — bare identifiers parse as instant vectors with a confusing "expected type string" error.
- **Multi-join `sum by` must keep the outer join key**: `sum by (persistentvolumeclaim)` drops `namespace`, silently emptying the outer `on(namespace, persistentvolumeclaim)` join — use `sum by (namespace, persistentvolumeclaim)`.
- **Grafana `label_values()` variable queries run as `/api/v1/series match[]` — selectors only**. A binary join inside a variable query (`label_values(a * on(...) b, label)`) fails with Prometheus' `1:62: parse error: unexpected <op:*>` (position = the `*` after the first selector), and Grafana's own label_values parsing can also emit `unexpected identifier` on complex exprs — the variable breaks, and any panel interpolating it (the logs panel via `${pods:regexformat}`) silently shows nothing. Panel queries are unaffected (query endpoint, joins legal there). Fix: chain selector-only hidden variables — `replicasets` = `label_values(kube_replicaset_owner{..., owner_name=~"$deployment"}, replicaset)` → `pods` = `label_values(kube_pod_owner{..., owner_name=~"$replicasets"}, pod)` (order in `templating.list` matters).
- Deployment variable uses a sentinel default: `includeAll: true` + `allValue: "__none__"` + current=All → "All" matches nothing, so the dashboard loads with no data ("default none selected" in #39) and Grafana can't auto-select a deployment. Every panel query embeds the deployment-guarded join, so the sentinel propagates everywhere. Grafana auto-selects the first value of a query variable on load — an empty `current` does NOT stay empty, hence the sentinel.
- **Log query UX** (2026-09-07): the logs panel takes a full **LogQL pipeline** via the `log_query` textbox — the panel expr is `{namespace=…, pod=~…} $log_query`, so the dropdowns own the selector and the variable is any pipeline chain (`| json | level="error"`, `|= "text"`, `| unpack | …`; empty = all logs). The preset strip is a text panel in **html mode** with button-styled links (same URL-param mechanics; presets: `| detected_level="error"`, `| detected_level="warn"`, `| json | level="error"`, `|= "error"`, clear). Buttons need `GF_PANELS_DISABLE_SANITIZE_HTML=true` on grafana (the sanitizer strips inline style attributes; acceptable because dashboard content is repo-authored only). Toolbar variables can't be widened in stock Grafana — full-width free-form querying is the logs panel's **panel menu → Explore**.
- Loki log selection: streams carry `instance` (`ns/pod:container`), `job`, `service_name`, `detected_level` — pod selection is an `instance` regex built from the deployment's pods (`${pods:regexformat}` in the query). Grafana datasource names are capitalized (`Prometheus`, `Loki`) though the GrafanaDatasource CRs are lowercase; datasource-type variables match by type, so the `${datasource}`/`${loki_ds}` indirection resolves either way.

## Alloy: `stage.pack` removed — lines are app-native now (2026-09-07, issue #39)

Every log line was wrapped as `{"_entry":"<original line>"}`: the `stage.pack` in `loki.process.wrap` packs its listed labels from the **label set**, but `loki.source.kubernetes` only emits `instance`/`job`/`service_name` — so the pack carried no metadata at all and just double-encoded every line (apps' own JSON nested-and-escaped inside `_entry`, which is what the #39 dashboard's logs panel showed). `config.alloy` now wires `loki.source.kubernetes` straight to `loki.write` — lines pass through as emitted (the logs panel parses native JSON/logfmt), k8s metadata stays on the `instance` label, and the expected `alloy_components` set is `discovery.kubernetes.pods` + `loki.source.kubernetes.pods` + `loki.write.endpoint` (no `loki.process`).

Two landmines hit while shipping it:
- **River comments are `//`, not `#`** — alloy's config language has no `#` comment (and backticks open raw strings): the new pods crashlooped at load (`expected identifier, got ILLEGAL`, `illegal character U+003A`) on a `#`-commented config. The rolling update kept the old pods serving, so no ingestion gap.
- **ConfigMap content edits did not reach the pod mounts** — `alloy-config` updated on the API server but all four pod volume mounts stayed stale 5+ min (first in-place CM update since the rebuild). Fix: `kubectl -n logging rollout restart daemonset/alloy` (same class as `docker restart sync-cloud-test`). Whether alloy hot-reloads is untested — the mount never refreshed to find out.

## Seaweed: all volumes read-only → loki flush failures for hours (2026-09-07)

While verifying the #39 dashboard, loki-0 was logging ~80/min `failed to flush ... S3: PutObject ... 500 InternalError` for 4h+ (ingester retries buffer the chunks — no data lost, memory stayed 404Mi). Triage path and findings:

- **Loki's S3 endpoint is seaweed, not rustfs** (`main-s3.objects.svc:8333` in `logging/loki-values.yaml`). The S3 gateway logged the real error: `No writable volumes and no free volumes left for collection:loki`; the filer's own metadata log was failing with the same assign error; the master logged `create 7 volume, created 0: Not enough data nodes found!`
- **All volume slots were full and read-only**: the volume server has a default max volume count (7 slots on one disk dir), loki chunks + thanos blocks filled them in ~12h, and volumes hitting `volumeSizeLimitMB: 1024` (`main.seaweed.yaml` master block) go read-only — with no free slot the master can't grow replacements, so every write path 500s at once.
- **The volume server was CPU-throttled at 93% of CFS periods** (vacuum/compaction churn after deletions) — the same starvation pattern the s3 gateway hit pre-#burn-in (documented in its comment in `main.seaweed.yaml`). It recovered only when the probe restarted the container (15:41): the fresh process re-registered, the master re-read post-vacuum volume sizes, and writes resumed. Flush errors went to 0 within a minute.
- **Fix**: volume server CPU limit 500m→1000m (`main.seaweed.yaml`) — same hottest-path logic as the s3 gateway's 1000m. Post-bump: throttling 0, flush errors 0.

Open follow-ups: **no alert fired** during the 4h+ of failed flushes — a ruler alert on loki flush failures (or seaweed writable-volume exhaustion) is the gap; and the 10Gi seaweed PVC now backs loki (30d retention) + thanos blocks — watch its growth, `allowVolumeExpansion: false` is deliberate so the only lever is retention/vacuum.

## Trivy cold-start race on fresh rebuild (2026-09-07, post-rebuild session)

On every fresh rebuild exactly one trivy scan pod errors: `scan-vulnerabilityreport-*` with `FATAL ... failed to store blob ... dial tcp trivy-service:4954: connect: connection refused`. The operator's Deployment goes ready ~16s before its first scan job (the cluster-SBOM scan), but the `trivy-server-0` cache-server StatefulSet — same helm release — starts ~75s later. The job hits the service while its endpoints are still empty.

What self-heals: the operator deletes the failed job (`scanJobsRetryDelay: 30s`) and re-queues *workload* scans — VulnerabilityReports accumulate normally. What does not: the `ClusterSbomReport` stays status-less — the operator treats the SBOM blob already cached on the server (`trivyServerHealthCheckCacheExpiration: 10h`, `cacheReportTTL: 120h`) as valid and does not re-scan, not even after an operator restart. Nothing local consumes ClusterSbomReport (the `TrivyCriticalImageVulnerabilities` alert runs off VulnerabilityReports), so the empty report is cosmetic; deleting it + restarting the operator did not force a regen — leave it for the TTL cycle.

`dependsOn: networking` (present pre-#31 on the kubescape-era security-config, lost in the refactor) would NOT have prevented this — the race is between two resources of one helm release, and networking/CNI was Ready ~2min before the scan job ran (the scan pod resolved the ClusterIP and got a backend-less refusal). Not restored; security's `wait: true` already implies CNI readiness.

Triage tells for next time: `kubectl -n security logs <pod>` shows `ClusterSbomReport` + connection refused (not image-pull or kyverno denial); trivy-server-0 `startedAt` is minutes after the failed job's `startTime`; the operator's reconciler-error spam on a fresh cluster (`... already exists` on configauditreports) is benign controller-cache racing, not related.

## kps uninstall remediation: bundle Namespace clobbered the PSS labels (2026-09-07, post-rebuild)

On the fresh rebuild the kube-prometheus-stack install failed 4× (timeout waiting for the node-exporter DaemonSet → uninstall remediation each time → Stalled). Root cause: **the monitoring namespace's PSS labels were gone** — node-exporter needs `enforce=privileged` (hostNetwork/hostPID/hostPath/hostPort) and PSS baseline denied every pod at creation (`Error creating: ... violates PodSecurity "baseline:latest"` — note this is kubelet PSS admission, NOT kyverno; kyverno never sees the pod and its report stays at 0 failures).

Mechanism: the thanos-operator bundle ships a `Namespace: thanos-operator-system`, and #31 renamed it onto `monitoring` so the operator lives in the group's namespace. **Both the `namespaces` and `thanos-operator` flux kustomizations apply as the same SSA field manager (`kustomize-controller`)** — whichever reconciles last rewrites the label map and prunes the other's fields (verified via managedFields: single Apply entry owning only the bundle's label set). Pre-rebuild this survived by luck (namespaces group happened to reconcile last); on a rebuild the order isn't guaranteed. Fix: the bundle's Namespace now carries the PSS labels via a strategic-merge patch in `monitoring/thanos-operator.kustomization.yaml` — both appliers declare the same load-bearing set, so order no longer matters. (Cosmetic label flip-flop between the two manifests may persist — harmless.)

Recovery sequence for a Stalled kps after the fix: PSS labels land (via the monitoring group reconciling the updated Kustomization CR — note `flux reconcile kustomization monitoring --with-source` BLOCKS on the group's health wait while kps is down; the CR spec still applies event-driven) → node-exporter DS FailedCreate retries succeed → but the release replays its terminal state (`RetriesExceeded`) → `flux suspend/resume helmrelease kube-prometheus-stack -n monitoring` forces a fresh install (helmrelease-stuck ladder step 2) → Ready=True.

Rebuild-path tell: a kps install timeout on node-exporter + `kubectl get events -n monitoring --field-selector reason=FailedCreate` showing PSS violations = this landmine. Also caught in passing: the cluster-rebuild skill's verification counts were stale (27→28 kustomizations, 16→15 helmreleases).
