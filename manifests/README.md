# manifests

Flux-managed manifest tree. There is no `kubectl apply` — everything here is mirrored into the `flux` bucket on rustfs by the sync container and reconciled by the root `Kustomization/local` (deployed by the terraform bootstrap, adopted and owned by the `flux-config` group). Pipeline mechanics and wedge recovery: [runbooks/local/pipeline-wedged.md](../runbooks/local/pipeline-wedged.md).

## Layout: bases + clusters

The tree splits by what varies between clusters (cmdshift/platform: multi-cluster prep):

- **`manifests/bases/<group>/`** — cluster-agnostic groups: HelmReleases + generic manifests shared by every cluster. Each dir has an explicit `kustomization.yaml` (registration-explicit everywhere; `kubectl kustomize` works in every dir now — no implicit-flux-only builds).
- **`manifests/clusters/<cluster>/`** — per-cluster overlay: the root kustomization, all group Kustomization CR files (`<group>.yaml`), and local-only overlay dirs. For the local cluster: `manifests/clusters/local/`, whose per-cluster notes live in [clusters/local/README.md](clusters/local/README.md).
- **`manifests/sources/`** — HelmRepository/GitRepository pins (shared).
- **`manifests/clusters/cloud/`** — cloud-side notes (not yet a built cluster).

Which tree a group deploys from is decided by its Kustomization CR's `spec.path`: `./manifests/bases/<group>` for pure-base groups, `./manifests/clusters/local/<group>` for groups with a local overlay (six overlay dirs — `certificates-config`, `networking-config`, `secrets-config`, `backups-config`, `observability-config`, `policies-config` — layer `../../../bases/<group>` via kustomize `resources:` plus local-only files), and `./manifests/clusters/local/flux-config` for the fully local-only group (no base dir; the former `objects-config` local-only overlay was removed with seaweedfs, cmdshift/platform#171). `./manifests/sources` serves the sources group.

The root Kustomization CR (`name: local`) lives at `manifests/clusters/local/flux-config/local.kustomization.yaml` with `path: ./manifests/clusters/local`; the bootstrap twin in `cluster/local/bootstrap/main.tf` must match that path — they are two copies of the same pointer and drift wedges bring-up.

Change history and dated learnings live in [CHANGELOG.md](../CHANGELOG.md); per-group decisions in each group's `README.md` (in `bases/`); procedures in `runbooks/local/`; landmine dispatchers in `.agents/skills/`.

## Groups and dependency order

Each `<group>.yaml` (in `clusters/local/`) is a flux Kustomization CR; its `spec.path` selects the build dir — the cluster-agnostic base in `manifests/bases/<group>/` or the per-cluster overlay in `manifests/clusters/local/<group>/`. `X` installs the operator/release, `X-config` applies that group's config objects (CRs, StorageClasses, exceptions, CNPs, rules) and gates them on real operator status via `healthCheckExprs`.

```
namespaces → access → sources → crds → secrets → secrets-config → certificates → certificates-config
→ networking → networking-config → flux → flux-config → policies → policies-config
→ security → security-config → storage → storage-config → datastores → datastores-config
→ observability → observability-config → backups → backups-config
→ scanning → scanning-config
```

(The `objects`/`objects-config` groups — seaweedfs, the LGTM stack's S3 backend — were removed with the OpenObserve migration, cmdshift/platform#171; `observability-config` now follows `observability` directly.)

Groups without a README are self-explanatory: `bases/crds/` (vendored/child-kustomization CRDs, `prune: false` — the prometheus-operator-crds HelmRelease was removed with the SM/PodMonitor CRDs in cmdshift/platform#146; the Alloy/PodLogs CRDs ship with the alloy-operator chart since cmdshift/platform#149), `manifests/sources/` (HelmRepository/GitRepository pins), `bases/namespaces/` (namespace manifests — **explicit resources list in `kustomization.yaml`; an unregistered `*.namespace.yaml` is silently inert**), `bases/access/` (human-facing RBAC: OIDC `groups` claim → bindings — `platform-admin` → built-in `cluster-admin`, `platform-view` → built-in `view` RoleBinding in `default` which excludes secrets; verified via `kubectl auth can-i --as/--as-group` impersonation and the `.tmp/kubeconfig-oidc` login, cmdshift/platform#91).

Group READMEs (under `bases/`): [networking](bases/networking/README.md) · [policies](bases/policies/README.md) · [secrets](bases/secrets/README.md) · [certificates](bases/certificates/README.md) · [storage](bases/storage/README.md) · [datastores](bases/datastores/README.md) · [observability](bases/observability/README.md) · [backups](bases/backups/README.md) · [security](bases/security/README.md) · [flux](bases/flux/README.md)

## Conventions

- **Namespace convention** — operators install into a namespace named after their kustomization group. Full mapping, migration rules, and traps: [runbooks/local/namespace-migration.md](../runbooks/local/namespace-migration.md).
- **Kustomization CR knobs carry their rationale in the owning group README, not the group list file** — `never prune` (flux-config: deleting the root GCs the tree), `prune on purpose` (security-config TracingPolicies retire by file deletion; policies-config test-bed posture with the `policy_report` tripwire), `no wait:true` on conditionless CRs, and the `force: true` bootstrap adoption story: [bases/flux/README.md](bases/flux/README.md), [bases/security/README.md](bases/security/README.md), [bases/policies-config/README.md](bases/policies-config/README.md).
- **valuesFrom everywhere** (cmdshift/platform#31): every HelmRelease ships values via configMapGenerator → `valuesFrom` — values live in a plain `<release>-values.yaml` next to the HelmRelease, generated as `ConfigMap/<release>-values` by the dir's `kustomization.yaml` with **per-entry `disableNameSuffixHash: true`** (`valuesFrom` is not a kustomize-known name reference, so a content-hash suffix would desync the hand-written reference; helm-controller re-reconciles on CM data changes anyway). Rationale comments move with the values; only local-only landmine notes stay inline. `helm_verify` resolves `valuesFrom` refs locally and renders the exact file flux ships. Gotcha: a values-only change doesn't re-trigger helm-controller — order is `flux_wait` (rebuilds the CM) then `helm_wait` per release; and the HR's `lastAttemptedConfigDigest` can stay frozen even then (suspend/uninstall/resume — the `helmrelease-stuck` skill).
- **Generated ConfigMaps stay under ~250KB** (cmdshift/platform#171): kustomize-controller's client-side-apply dry-run embeds object content in `last-applied-configuration` (~256KB cap — NOT the 1MiB CM data limit); one oversize object fails the whole group's dry-run. Split large generated content (dashboards, rules) by domain into separate configMapGenerator entries; `dryrun_check` reports the failing object.
- **Registration is explicit**: every yaml in a dir must be listed in that dir's `kustomization.yaml` `resources:` (values files excepted — generator inputs). Unregistered files are silently not built and flux prunes them from the cluster. Same for the `bases/namespaces/` list. Every dir — including the nine that previously relied on flux's implicit kustomization — now carries an explicit `kustomization.yaml`, so local `kubectl kustomize` matches the flux build everywhere.
- **Explicit `metadata.namespace` on every HelmRelease** — the HR namespace is the release target; no kustomize `namespace:` transformers (they clobber explicit fields). Sole exception: the `bases/datastores` kustomization sets `namespace: datastores` (every HelmRelease there pins the matching namespace explicitly).
- **CR-managed workloads** (seaweed cluster was the last one — the group is gone; grafana/the Alloy collectors went with the OpenObserve migration, cmdshift/platform#171): resources and securityContext go in the CR spec, not helm values. The Alloy CRD notes below are retained for any future operator-CR adoption. Note the Alloy CRD is schema-less: a typo'd `spec` field passes `cr_validate` and the operator silently drops it — check field names against the chart values the operator maps onto (cmdshift/platform#155).
- **Dependency rules**: a group naming `storageClassName: local-path` must `dependsOn: storage-config` (the SCs moved out of `storage`); CRs whose CRDs a release's operator creates live in a group that `dependsOn` that release, never the reverse; admission-critical PolicyExceptions go in the early `policies-config/` group.
- **Local-only markers**: `# remove in the cloud` and `# true in the cloud` flag deliberately local-only settings at the value; the cloud-side actions are collected in [manifests/clusters/cloud/notes.md](clusters/cloud/notes.md).
- **Comment rules** (cmdshift/platform#43, cmdshift/platform#136): default no comment, max 3 lines; bug/landmine issue refs only — full rules in the `writing-code` skill's [Comments section](../.agents/skills/writing-code/SKILL.md); worked examples + marker vocabulary in [runbooks/local/code-comments.md](../runbooks/local/code-comments.md).
- **Compute quotas** (cmdshift/platform#93): every workload namespace carries a `ResourceQuota/compute` in its group's `-config/` dir as `resource-quota.yaml` — sized 2× audited aggregate requests + headroom, limits ≥ current limits sum with burst headroom, pods ≈ 2× running count; the evidence numbers live in each quota's rationale comment, not here. Every group's config kustomization includes it (the explicit-resources dirs — `observability-config/`, `storage-config/` — list `resource-quota.yaml` in `resources:`; registration is explicit everywhere now, so `kubectl kustomize` reflects the real build — still don't use it as a completeness check for what flux will apply). New deployments must fit within the target namespace's quota — a blocked deployment shows as StartError/FailedCreate with `exceeded quota`; add the workload and bump the quota in the same change if it doesn't fit. **LimitRange defaults are NOT dead code for PolicyException-exempt containers** (cmdshift/platform#111): kyverno skips them but ResourceQuota admission does not — a quota-denied create wedges the controller. `observability` carries `LimitRange/compute-defaults` (`bases/observability-config/limit-range.yaml`) for exactly that case (introduced for the thanos-operator's config-reloader — operator gone since cmdshift/platform#128, LimitRange stays); other namespaces with exception-exempt containers need the same. The observability namespace also carries the former `logging` quota as `logging-resource-quota.yaml` (name `logging-compute` — two quotas named `compute` in one namespace would both charge every pod; cmdshift/platform#120). The cloud-side framing (LimitRange as the defaults source where admission policy may differ) is unchanged — see [manifests/clusters/cloud/notes.md](clusters/cloud/notes.md).

## Admission policy

All kyverno ValidatingPolicies (13) run in **Deny** mode — the requirements (requests/limits, pinned tags, runAsNonRoot, seccomp, caps dropped) and per-policy details live in [policies/README.md](bases/policies/README.md); the checklist for new workloads is [runbooks/local/adding-a-workload.md](../runbooks/local/adding-a-workload.md). PolicyExceptions live in `policies-config/` (with kyverno, per the namespace convention) and cover deliberate Talos-in-Docker settings — don't try to "fix" those workloads.

**PDB baseline** (cmdshift/platform#84): every multi-replica workload must have a PodDisruptionBudget (maxUnavailable: 1) — generated by the `auto-pod-disruption-budget-multi-replica` GeneratingPolicy in `policies-config/` for flux-managed namespaces, explicit manifests there for kube-system workloads. Escape hatch: label the workload `pdb.kyverno.io/skip: "true"`. This is also the first generate-rule precedent, with a kube-system gotcha: **a kyverno CEL policy's fine-grained webhook inherits `config.webhooks.namespaceSelector` from the kyverno values, which excludes kube-system — a GeneratingPolicy silently generates nothing there**; details in [policies-config/README.md](bases/policies-config/README.md).

## Hardening baseline: accepted deviations

The NSA-guidance hardening settings stay in the manifests; every deviation below is deliberate, maps to a kyverno PolicyException or an upstream/CRD limitation, and is the baseline the hardening tools (tetragon: runtime, trivy-operator: static, kube-bench: episodic CIS) audit against — keep it current when adding workloads:

- **thanos CR-managed pods (query/compact/store/ruler)** — REMOVED with the LGTM migration (cmdshift/platform#128). Mimir then ran fully hardened — REMOVED with the OpenObserve migration (cmdshift/platform#171), as were seaweed `main-master` and loki/alloy (no roFS for seaweed master; loki/alloy kept SA tokens + alloy ran as root for the host-log mounts — the `allow-openobserve-collector-host-access` PolicyException is the current host-log deviation).
- **velero deployment** — the chart only exposes pod-level `securityContext` and renders it into its CRD-upgrade hook jobs too, where `allowPrivilegeEscalation` is not a legal pod field (SSA rejects it, helm upgrade fails) — pod SC must stay pod-legal fields only (runAsNonRoot/runAsUser/seccompProfile). Pod-level `runAsUser: 0` → now `runAsNonRoot: true, runAsUser: 1002` (numeric: the image's USER `cnb` is non-numeric and kubelet can't verify runAsNonRoot against a bare username; the node-agent container keeps its own override). The velero container itself is container-hardened via the chart's `containerSecurityContext` (APE false, caps drop ALL, seccomp — it also propagates into the v1.18 kopia maintenance Jobs, which copy the deployment's contexts); only the node-agent container remains privileged (`# remove in the cloud`) and the aws-plugin initContainer unchanged. Maintenance-Job details: [backups/README.md](bases/backups/README.md) (cmdshift/platform#109).
- **openobserve-collector (agent DaemonSet)** — runs as root with host-path mounts (`/var/log/pods`, container logs, `/hostfs` for hostmetrics): the image declares no USER and the filelog/hostmetrics presets need host log + procfs access; covered by `allow-openobserve-collector-host-access` (host-path/nonroot/caps, name-prefix match — cmdshift/platform#171). The gateway Deployment runs fully hardened (nonroot, roFS, caps dropped) — no deviation.
- **kubernetes/Talos defaults** — the `system:*` discovery/basic-user ClusterRoleBindings, `cluster-admin → system:masters`, and Talos-rendered statics are stock bootstrap, not manifest-owned.
- **ConfigMap regex false positives** — findings on config keys (cilium-config, kyverno/logging CMs) are verified non-credentials.
- **metrics-server** — the fix-first success: container-level `securityContext` with `runAsGroup: 1000` cleared the finding, no exception needed.

Learnings that generalize: explicit container-level `runAsGroup` is the common gap (charts set pod-level non-root or uid-only, leaving gid implicit 0 — set uid/gid explicitly wherever the chart allows); **the flux2 chart securityContext REPLACES, not merges** (templates hardcode container-sc defaults behind an if/else — spell out the full map or you silently drop APE/caps/roFS); non-root retrofits need a **numeric** `runAsUser` when the image declares a bare username like `USER "nobody"` (kubelet can't verify `runAsNonRoot` against it), plus a one-time PVC `chown` for pre-existing root-owned data (helper-pod pattern).

## Out-of-cluster companions

rustfs S3, secrets server, haproxy, mailpit, sync container, caching registry, rauthy — terraform/docker in `cluster/local/`, none exist in the cloud, so CNP `toFQDNs` rules, the Bucket endpoint, the ClusterSecretStore URL, O2's SMTP host, and the BSL `s3Url` all resolve differently there. The `*.cloud.test` companions serve **dual-mode** (cmdshift/platform#130): https on :443 (TLS terminated at the external haproxy with a `*.cloud.test` wildcard leaf from the platform intermediate) alongside the historical plain :80 — :80 redirects browsers to https (User-Agent contains Mozilla/5.0; machine clients are unaffected, so no consumer migration is needed), while cluster consumers (flux bucket, ESO store, velero BSL, registry mirror) deliberately stay on :80 until the OIDC-keycloak migration migrates them (cmdshift/platform#131). Rauthy (`auth.cloud.test`, cmdshift/platform#154, replacing keycloak) serves OIDC for the kube-apiserver — it is the single issuer (Dex rejected); the `access/` group maps its `groups` claim to RBAC (see below). Topology and landmines: [runbooks/local/cluster-rebuild.md](../runbooks/local/cluster-rebuild.md).
