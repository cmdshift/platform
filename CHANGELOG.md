Narrative log of the platform's evolution, newest first. Dated learnings, incident stories, and decision history live here; durable procedures live in `runbooks/local/`, timeless per-group decisions in `manifests/local/*/README.md`, and landmines in `.agents/skills/`. ## 2026-09-16

- **Agent skills: the process layer added (cmdshift/platform#118)** — five new skills drafted by sweeping existing docs, plus a `platform-workflow` branch gate. `planning-changes` (surface mapping group vs `-config/`, dependency sequencing, rationale-comment check, branch first), `writing-code` (no-live-patches, `<name>.<kind>.yaml` naming, valuesFrom pattern, fully-qualified refs, evidence-based sizing, admission-before-writing), `making-a-commit` (conventional `<scope>: <summary>` format from the merge history, natural splits, docs gate, **commit-by-permission as a hard stop**: propose then wait for explicit approval — the wait exists so the human can read the diff, and a pre-review go-ahead doesn't authorize the commit; **commit signing rule**: commits must be signed when the developer signs, any gpg failure = stop and hand back, no troubleshooting, wait if the human isn't present — unsigned commits and retry loops are both out), `opening-a-pull-request` (pre-PR gates, `Closes cmdshift/platform#N` linkage, verification receipts in the body), `skill-improvement` (thin-dispatcher shape, trap-list currency, AGENTS.md table sync). `platform-workflow` gained step 0: never work on `main`, verify/create `feat/`/`fix/` branch before the first edit. All six synced into the AGENTS.md dispatch table. Decision: skills are self-contained (docs-sweep pattern) rather than runbook-paired — none of these need worked examples beyond what the skill carries; branch-prefix convention is enforced, not just documented (merge-history precedent).

- **Admission posture: `policies` + `policies-config` now prune** (cmdshift/platform#84 follow-up): the two kustomizations had `prune: false` because an auto-deleted PolicyException in a Deny-mode cluster was a silent *deferred* outage — the reconcile goes green, pods keep running, and only a restart hours later gets denied at admission. The posture flipped to `prune: true` (test-bed: deletions are git-reviewed in PRs) because the latent failure mode has a built-in tripwire: kyverno **background scans ignore the webhook namespaceSelector** and still validate pods against the policy registry, so a GC'd PolicyException surfaces as `policy_report` failures ≠ 0 within one scan cycle (≤1h) — the standard post-change check anyway. `crds/`, `namespaces/`, and `flux-config` keep `prune: false` (CRD/namespace/root-tree deletion is cluster-breaking, not a posture question). Consequence: renames/deletes of exception/policy/PDB files now GC their objects (the rename of the GeneratingPolicy left the old object behind under the old posture — it had to be `kubectl delete`d by hand); zero-gap namespace moves of exceptions now need manual sequencing (runbooks/local/namespace-migration.md updated).

- **Pod disruption budgets for every multi-replica workload (cmdshift/platform#84)**: new `manifests/local/policies-config/auto-pod-disruption-budget-multi-replica.generating-policy.yaml` — the repo's first kyverno **GeneratingPolicy** (CEL API, `policies.kyverno.io/v1`, kyverno 1.19.1). It generates a `PodDisruptionBudget` (maxUnavailable: 1) for every apps/v1 Deployment/StatefulSet with replicas > 1 in flux-managed namespaces, via `generate.template` with `interpolate: cel` (`(( ... ))` placeholders), `evaluation.generateExisting.enabled` (catches pre-existing workloads) and `synchronize.enabled` (drift-heal + delete-on-trigger-delete). Design decision: **maxUnavailable: 1, not the issue's minAvailable: 1 candidate** — maxUnavailable caps concurrent voluntary evictions at 1 regardless of replica count; minAvailable: 1 would let a 3-replica database lose 2 at once. Escape hatch for charts shipping their own PDB: label the workload `pdb.kyverno.io/skip: "true"` (overlapping PDBs over-restrict evictions — the most restrictive wins). Survey at adoption: only 2 multi-replica workloads cluster-wide, both in kube-system — coredns (2) and cilium-operator (2); all 11 StatefulSets are replicas=1. Both coredns replicas were observed co-located on one worker node (work-local-test-2d17) — exactly the simultaneous-eviction scenario the issue describes. The real payoff is future multi-replica databases: cloudnative-pg is already deployed in `datastores/`.
- **LANDMINE — a kyverno CEL GeneratingPolicy can NEVER see workloads in kube-system, silently** (cmdshift/platform#84): kyverno builds a fine-grained webhook per CEL policy (e.g. `gpol.validate.kyverno.svc-ignore-finegrained-<policy-name>` in validatingwebhookconfigurations) and that webhook's namespaceSelector **inherits `config.webhooks.namespaceSelector` from our kyverno helm values** (`policies/kyverno-values.yaml`), which NotIn-excludes kube-system/kube-public/kube-node-lease/flux-system/policies. So the background-controller simply never enqueues UpdateRequests for kube-system triggers — no error, no event, no log anywhere; the symptom was a silently-empty generated-PDB list (evidence: background-controller trace logs showed an UpdateRequest for every trigger EXCEPT the kube-system ones). Consequence: the two kube-system multi-replica workloads (coredns, cilium-operator) get **explicit PDB manifests** in `policies-config/` (`coredns.pod-disruption-budget.yaml`, `cilium-operator.pod-disruption-budget.yaml`, both maxUnavailable: 1). coredns has a second reason to be explicit: it's talos-bootstrap-owned, not flux-managed, so a generate path couldn't own it anyway. The explicit PDBs live in `policies-config/` deliberately — that kustomization owns cluster-protection objects. Timeless rule → [manifests/local/policies-config/README.md](manifests/local/policies-config/README.md) + AGENTS.md admission section; cloud note: same webhook exclusion applies — verify databases actually get PDBs and add explicit ones for any multi-replica kube-system workload ([manifests/cloud/notes.md](manifests/cloud/notes.md)).
- **PDB acceptance check**: policy status WebhookConfigured + RBACPermissionsGranted; both PDBs report ALLOWED DISRUPTIONS 1; `policy_report` failures 0; all 22 HelmReleases True. Drain test of work-local-test-2d17 with `--pod-selector k8s-app=kube-dns` run as the acceptance check — evictions serialize behind the PDB.
- **InfoInhibitor disabled — a chart alert whose only consumer is the chart's own inhibit_rules is dead weight when the Alertmanager config is CR-managed** (cmdshift/platform#114): `defaultRules.disabled.InfoInhibitor: true` in `monitoring/kube-prometheus-stack-values.yaml`. ## 2026-09-14

- **cmdshift/platform#109 fixed fix-first: velero kopia repo-maintenance Jobs hardened at the source — no PolicyException**. Root cause: velero's server builds the maintenance-job pod spec internally (`pkg/repository/maintenance` buildJob) with no securityContext/resources — 4 policies denied every Job since repo creation (Warning events every ~5m, all 9 BackupRepositories Failed). Two-part fix: (a) v1.18 maintenance-job pods **copy the velero deployment's pod- and container-level securityContext**, so `podSecurityContext` (runAsNonRoot, `runAsUser: 1002`, seccomp RuntimeDefault) + `containerSecurityContext` (APE false, caps drop ALL, seccomp) in `backups/velero-values.yaml` hardened the velero deployment AND the maintenance Jobs at once — retiring the "container-level hardening unreachable via values" deviation in `manifests/local/README.md`; (b) `require-resource-limits` fixed via `podResources` under `configuration.repositoryMaintenanceJob.repositoryConfigData.global` (the repo-maintenance ConfigMap), sized like the data-mover pods (cpu 50m/1000m, mem 256Mi/512Mi).
