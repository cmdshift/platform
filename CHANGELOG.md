# Changelog

Narrative log of the platform's evolution, newest first. Dated learnings, incident stories, and decision history live here; durable procedures live in `runbooks/local/`, timeless per-group decisions in `manifests/bases/*/README.md`, and landmines in `.agents/skills/`. Issue/PR references use the `cmdshift/platform#N` form.

## 2026-09-25 (rauthy replaces keycloak as the OIDC issuer; memory −2.75Gi)

- **Keycloak → Rauthy 0.36.2** (cmdshift/platform#154, `cluster/local/auth/` rewritten): "keycloak is simply too fat" — the JVM companion needed 3Gi (2 OOM-kills during realm import, cmdshift/platform#131); rauthy (Rust + embedded Hiqlite) runs at **256Mi, settled ~46MiB**. Same companion shape: `auth-cloud-test` at `10.0.128.9:8080`, TLS at the external haproxy, alias unchanged — no consumer moves. Issuer changed `https://auth.cloud.test/realms/platform` → `https://auth.cloud.test/auth/v1/` (**trailing slash load-bearing** — apiserver exact-matches the flag against discovery's `iss`), so `cluster.tftpl.yaml` extraArgs, `kubeconfig-oidc`, and the three access/ auth-proxy values all moved; **machine-config template change = full rebuild** (the cmdshift/platform#140 rule). Fixtures kept semantic-equivalent: groups `platform-admin`/`platform-view` (now rauthy **groups**, not realm roles — `groups` claim verified to ride access+id tokens when in the client's `default_scopes`), admin/admin123 (renamed from `test`, carries `platform-admin`), viewer/viewer123 (`platform-view`); both clients pinned **RS256** (rauthy's EdDSA default is unvalidatable by the kube-apiserver). Rauthy validation traps that cost a container cycle each: bootstrap JSON is **first-boot only** (wipe-on-recreate mirrors the old keycloak semantics — data in the container layer); the **config parser panics on unknown keys** (0.36 strict); confidential client secrets need **≥64 chars and alphanumeric-only** (hyphens pass bootstrap then brick the token endpoint — the secrets-server `client-secret` moved with it); group ids are internally allocated (`^[a-zA-Z0-9]{24}$` — don't set them); `bootstrap.admin_email` renames the built-in admin **before** users.json is read (email UNIQUE collision — keep the built-in at admin@localhost). The auth-proxy HelmReleases needed a manual `reconcile.fluxcd.io/requestedAt` annotate — values-ConfigMap-only changes don't re-trigger chart release on this flux pin. Verified on the post-swap full rebuild: OIDC chain end-to-end (discovery exact-match, admin `get nodes` via kubelogin, viewer Forbidden/allowed matrix, token claims decoded — `groups` rides RS256 tokens when in `default_scopes`); one real trap surfaced — **kubelogin sends `redirect_uri=http://localhost:8000` (bare host, no path)** and rauthy exact-matches redirect URIs (no wildcards): keycloak's `http://localhost:8000/*` shape bricks the flow with a 400 "invalid redirect uri" — register the bare host. Also learned: stale `_oauth2_proxy` sessions survive an IdP swap (cookie-secret stable + session-in-cookie + refresh disabled → dead keycloak identities keep validating); rotate the cookie-secret on IdP migrations for a clean cut (landmine in access/README).

## 2026-09-25 (admin ingress live: oauth2-proxy per app; cilium 1.20.2 + ztunnel removed)

- **Admin ingress landed: oauth2-proxy per app behind the Gateway** (cmdshift/platform#41, `manifests/bases/access/`): `grafana.local.test` / `hubble.local.test` / `seaweed.local.test` (the **filer** UI, not master) all proxy-authed via Keycloak PKCE, cross-app SSO via the Keycloak session (proxy cookies are **host-scoped** — a shared `.local.test` cookie would leak the admin bearer credential to any future 3rd-party host under the domain; SameSite can't prevent it since all `*.local.test` hosts are one site), full matrix green (grafana `api/user` external identity). Shape: one oauth2-proxy HelmRelease per app in the new `access` namespace (legacy oauth2-proxy picks upstreams by path, not Host — one instance can't fan out subdomains; subdomains over path prefixes because hubble-ui has no base-path support), HTTPRoutes parented to `local-test`'s `https-wildcard` listener, ReferenceGrants in the target namespaces (`access`→`observability`/`kube-system`/`objects`), Keycloak client in realm.json (recreate the auth container after realm edits), secrets via one `access/oauth2-proxy-credentials` server path + `access/platform-root-ca` (IdP trust via `--provider-ca-file` + `--use-system-trust-store` — NOT `--ssl-cert-file`, that's the server-cert flag). The 403 debugging arc produced three durable rules, all in [access/README.md](manifests/bases/access/README.md): (1) **the gateway L7LB enforces its own egress policy at the matched-route→upstream step** — `allow-ingress-proxy-egress` CCNP (`reserved:ingress`→`cluster`+`host`) is load-bearing; without it every route 403s "Access denied" from cilium-Envoy while direct pod curls 302 fine (cilium/cilium#47617, #43519); (2) **CNP egress enforces post-DNAT targetPorts** — hubble-ui needs `8081`, not svc port `80` (grafana/seaweed worked by coincidence); (3) the webhook secrets provider ignores `remoteRef.property` — per-key `data` entries deliver the whole JSON envelope (the "cookie_secret must be 16/24/32 bytes, is 64" crash). Grafana reads `X-Forwarded-Email` (pass_user_headers default); `X-Auth-Request-*` only rides the auth flow. Access group `dependsOn` grew `sources`/`secrets-config`/`networking-config`/`policies`, timeout 2m→10m (5m health-check timed out mid-install AND blocked each retry for its full duration).
- **Cilium 1.20.2 (stable) + ztunnel removed** (cmdshift/platform#41): the kernel-7.2 pre-release pin's reason is gone — 1.20.2 ships the FnSetRetval verifier fix (`b73ca6e8`, cilium/cilium#48016 closed) — so the pin dropped to `1.20.2` in both the HelmRelease and the bootstrap twin. ztunnel exists only in the 1.21-pre line: the same change removed `encryption.type: ztunnel` (→ wireguard), the cert-manager ztunnel CA Certificates (+ their healthCheckExpr), the HelmRelease `postRenderers` (chart-shape-coupled `/etc/ztunnel` secret remap), and the `ztunnel-cilium` PolicyException match. Verified post-upgrade: agents rolled to v1.20.2, `Encryption: Wireguard`, Gateway `Programmed`, admin-ingress matrix green. Ztunnel resurrect-from-git-history is documented in networking/README (don't re-derive the PKCS#8/CA:FALSE cert constraints from memory). Cilium-agent memory bumped 448/672→512/768Mi: live OOM on the busiest node (368Mi steady) after the Gateway routes landed — `ContainerOOMKilled` alert fired to mailpit, re-sized per the audit convention.
- **`access.yaml` flux shape** (cmdshift/platform#41): the new namespace lives in `namespaces/` (explicit resource list — an unregistered file silently hangs dependents); `networking-config/` gained the access CNP, the ingress-proxy-egress CCNP, and the kube-system ReferenceGrant (the ns is cluster-owned, not flux-created); `observability-config`/`objects-config` own their namespace's grants. The secrets-server seeded two new paths; the auth module's terraform state now carries the recreated keycloak container.

- **INCIDENT: the configless boot experiment failed behind the leastconn LB** (validated live, cost a full apply failure) — `USERDATA` was pulled to boot nodes configless (maintenance mode), but provisioning through the cmd LB fails **nondeterministically**: worker applies got `certificate signed by unknown authority` (the LB routes CA-verified TLS to still-maintenance nodes presenting self-signed certs) and bootstrap got `bootstrap is only available on control plane nodes`. A maintenance-mode apid is unauthenticated/self-signed — **any leastconn LB in front of a mixed configured/maintenance backend pool breaks CA-verified provisioning**; USERDATA is what makes the LB shape safe. USERDATA + `lifecycle { ignore_changes = [env] }` restored; with USERDATA the cmdshift/platform#73 `talos_machine_configuration_apply` resources were converge no-ops at first boot and were **deleted** from `nodes/main.tf`. Consequence: **machine-config template changes require a full cluster rebuild again** — the #73 "iterate via terraform apply" path is gone; the runbook + ARCHITECTURE + incidents post-mortem carry the corrected rule.
- **DNS**: the `cmd` A-record is restored in `dns/templates/local.tftpl.zone` (cmd.local.test → 10.0.8.1); the dns module takes a `cmd` variable again.
- **LANDMINE (cmdshift/platform#149 follow-up, found on this rebuild): the three Alloy CRs lived in the same kustomization as the alloy-operator HelmRelease that ships the Alloy/PodLogs CRDs** — on a fresh cluster the root dry-run of the CRs fails (`no matches for kind "Alloy" in version "collectors.grafana.com/v1alpha1"`) and wedges the whole observability group. Fixed by git-mv of `alloy-{logging,platform,telemetry}.alloy.yaml` into `manifests/bases/observability-config/` (which dependsOn observability) + kustomization.yaml updates in both dirs; the observability README's file-layout section corrected. Same rule as the generic "CRs live in a group that dependsOn the release creating their CRDs" — the instantiation-of-the-rule is what was missing here.
- **New flux edge**: the `security` Kustomization gained `dependsOn: storage-config` — trivy-server's local-path PVC sat Pending (unbound PVC) without it (cmdshift/platform#140 rebuild). Recorded in the security README.
- **Docs corrections from the topology change**: published-ports 6443/50000 moved from the ctrl container to the `cmd` container in every surface (the stale-binding recovery filter is now `name=cmd-local-test` — a restart is an LB blip, not a node reboot); the runbook's "multi-ctrl ceiling" note is retired (Linux evidence exists, knob restored); ARCHITECTURE.md topology/address-table/published-ports/memory-budget updated; nodes publish no host ports at all and talosctl reaches every apid through the cmd LB (`cmd.local.test:50000`).

## 2026-09-24 (Alloy CR architecture: k8s-monitoring removed, operator + 3 collectors)

- **cmdshift/platform#149 landed on branch `feat/k8s-monitoring`**: the hand-configured `alloy-logging`/`alloy-telemetry` HelmReleases and the k8s-monitoring chart (v4.5.2) are replaced by the final architecture — three `Alloy` CRs (**alloy-telemetry** STS: cluster plumbing — kubelet/cadvisor/apiserver/kcm/scheduler, ksm + node-exporter targets, OTLP traces intake; **alloy-platform** STS: per-service scrape families + collector self-scrapes; **alloy-logging** DS: pod logs + audit tail), each fed a raw `.alloy` file via configMapGenerator and reconciled by a standalone `alloy-operator` HelmRelease (grafana 0.7.1 — ships the Alloy+PodLogs CRDs). kube-state-metrics (prometheus-community 8.5.0) and prometheus-node-exporter (4.57.0) are standalone HelmReleases again. The chart was removed as "not pulling its weight": it validated at least one collector (no installer-only mode), generated Alloy CRs with a nameless `configMap` block, needed hook-job resources under kyverno, and its hostMetrics label-matching pulled unrelated pods into `job=node-exporter` — the raw-CR path expresses everything the experiment needed with none of the parent-chart machinery.
- **LANDMINE (cost debugging rounds): the k8s-monitoring chart's generated Alloy CR sets `alloy.configMap: {create: false}` WITHOUT a `name`** (cmdshift/platform#149) — the alloy-operator then defaults the mounted CM name to `<cr-name>-config`, and if another CM exists under that name (e.g. an old generator's), pods silently mount STALE config. Fix pattern: always set `configMap: {create: false, name: <fullname>}` explicitly. The final CRs carry this (name = the configMapGenerator output).
- **LANDMINE: an operator-managed release collides with a same-named flux HelmRelease's release storage** — "upgrade failed; rollback required" fights (immutable StatefulSet fields: volumeClaimTemplates, selector) and version churn (cmdshift/platform#149). When migrating a workload to an Alloy CR, the CR's release name must be fresh OR the old release storage must be purged first (`sh.helm.release.v1.<name>.*` secrets + HR deletion).
- **LANDMINE: the operator auto-creates the per-Alloy ClusterRole** (named after the CR) and it INCLUDES `nodes/metrics`, `nodes/pods`, `nonResourceURLs /metrics` — kubelet/cadvisor scrapes need no custom RBAC (cmdshift/platform#149). A hand-written ClusterRole with the same name collides with the operator's helm install ("cannot be imported into the current release: invalid ownership metadata") — delete it and let the operator own it (`alloy-telemetry.rbac.yaml` is gone).
- **LANDMINE: the chart's hostMetrics `labelMatchers` must use `app.kubernetes.io/name=node-exporter`, never `app.kubernetes.io/instance`** (cmdshift/platform#149) — the chart's instance label is shared by ALL chart-deployed pods and the feature's pod-role discovery has no port-name filter, so wrong labelMatchers scrape unrelated pods as node-exporter (operator + ksm observed).
- **LANDMINE: kyverno admission applies to helm hook jobs too**, cmdshift/platform#149 — the chart's `waitForAlloyRemoval` hooks failed `require-resource-limits` until `alloy-operator.waitForAlloyRemoval.resources` was set, and a failed uninstall-remediation hook wedged the release in `uninstalling` state ("Could not determine release state"); recovery: suspend HR → delete `sh.helm.release.v1.<release>.*` secrets → resume → fresh install. Same session, self-inflicted: **duplicate top-level YAML keys silently overwrite** (two `telemetryServices:` blocks — last wins) — caught only because the hook-job resources never appeared in the CM.
- **LANDMINE (cost debugging rounds): the companion haproxy OOM-killed (exit 137) under sustained S3 mirroring traffic**, cmdshift/platform#149 — the cloud-test container's 256M docker limit (sized for TLS termination, not sustained S3) starved under the observability pipeline's mirror load; bumped 256→512 in `cluster/local/external/main.tf`. Symptom chain: source-controller Bucket main fails "no route to host", sync container logs `mirror failed; retrying`, `sync_wait` hangs forever — and CMs silently go stale (the cluster keeps running OLD config while looking healthy). Recovery: `docker start cloud-test` + `flux reconcile source bucket main` — and verify CM CONTENT, not just sync_wait convergence.
- **LANDMINE: bash `a || b && c` parses as `(a || b) && c`** (cmdshift/platform#149) — `prometheus_query`/`loki_query`'s `REPO_ROOT="$(git ... || cd ... && pwd)"` ran the fallback `cd && pwd` EVEN ON SUCCESS, appending a second line to REPO_ROOT → garbage LOCK_DIR → the shared port-forward lock was never found → "port-forward failed to establish" on every call. Fixed with `{ cd ...; pwd; }` grouping; the two scripts stay in lockstep.
- **ksm double-target (:8081) phantom disappeared with the standalone ksm release — never root-caused.** If it reappears: check `prometheus_scrape_targets_gauge{component_id="prometheus.scrape.kube_state_metrics"}` on the collector's /metrics. The keep-rules in the `.alloy` configs select services by `namespace;instance-label;name-label` — ksm/node-exporter release names (and instance labels) changed twice during the migration; the final names are `kube-state-metrics` / `prometheus-node-exporter`.
- The `observability` quota was bumped for the migration's parallel window (both alloy stacks + the operator live simultaneously): requests.cpu 2→3, requests.memory 8Gi→10Gi, limits.cpu 16→20, limits.memory 12Gi→16Gi, pods 24→32 — commit 2 (old releases deleted) sheds ~7 pods back.
- Old k8s-monitoring HR deletion left its helm release deployed (helm-controller's pre-delete hook race — flux did not uninstall); required a direct `helm uninstall k8s-monitoring -n observability`. The standalone alloy-operator chart has NO waitForAlloyRemoval hooks (parent-chart-only) — flux GC + the operator's uninstall finalizer cover cleanup.

## 2026-09-22 (Prometheus removed, OTel completes the metrics path)

- **Prometheus is gone — the OTel collector is the sole scraper; mimir the store; a chart-managed Alertmanager the routing** (cmdshift/platform#141, branch `feat/remove-prometheus`). kube-prometheus-stack (operator + Prometheus CR + all its generated SMs/secret relabeling) deleted; `prometheus-operator-crds` STAYS in `crds/` (CRDs-only release, no pods — the target allocator's `prometheusCR` discovery and the ~14 remaining ServiceMonitors across 11 groups need the SM CRDs; deleting the CRDs would have forced hand-writing every scrape job). The OpenTelemetryCollector CR became `mode: statefulset` with `targetAllocator.prometheusCR` enabled (empty selectors = select ALL — an omitted selector matches nothing silently), a `prometheus` receiver pushing to mimir via `prometheusremotewrite` (timeout 30s, queue 10000×10 consumers), and static `scrape_configs` for the control-plane targets SMs can't express: kubelet/cadvisor via node-role SD + collector SA token, apiserver via the default-ns endpoints SD (needs a `nonResourceURLs: ["/metrics"]` ClusterRole rule — kubelet-style SARs otherwise), kube-controller-manager/kube-scheduler via pod SD + `pod_host_ip:10257/10259` rewrites. kubernetes-mixin essentials ported into `mimir-rules.yaml` (Watchdog heartbeat, KubeNodeNotReady, KubeDeploymentReplicasMismatch, KubeJobFailed — ksm v2 has no `kube_job_status_stage`); the CR-managed Alertmanager was replaced by the `prometheus-community/alertmanager` chart (1.43.3) with the mail routing inlined as plain config and `alertmanager-operated` → `alertmanager` repointed in mimir.config, loki-values, and the flux provider.

Second hit: the TA SA (`otel-collector-targetallocator`) needs its own ClusterRoleBinding PLUS `scrapeconfigs`/`probes` get-list-watch and `secrets`/`configmaps` list-watch (promOperator CRD watcher builds informers over them — missing RBAC crashloops the TA at startup).
